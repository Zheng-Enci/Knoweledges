# LLM Wiki 是什么：为什么都说它能替代 RAG，一次讲清摄入时编译与查询时检索的本质区别

> **核心结论**：LLM Wiki 不是一款产品，而是一种知识库写法——把「每次提问现检索」换成「入库时先编译」。传统 RAG（Retrieval-Augmented Generation，检索增强生成）在导入时只做切块和向量化，真正的理解留到用户提问那一刻；LLM Wiki 让模型在导入时通读全部原始文档，直接写出一套带摘要和语义内链的 Markdown 页面，提问时只定位页面、不再拼接碎片。它之所以被说成「替代 RAG」，是因为在约 100 个信息源、几百个页面的规模内，它省掉了整套向量基础设施，且答案有结构；但它有四个绕不开的边界（规模、精度、时效、沉没成本），超过阈值后仍需检索兜底。结论不是谁淘汰谁，而是**高频稳定的知识先编译，长尾细节仍靠检索**。

## 1. 先给结论：它替代的是「查询时做功」（Query-time Compute）

2026 年 4 月，Andrej Karpathy 在 GitHub 上放出一份 Gist（代码片段文档），提出 LLM Wiki 的构想：用 LLM 把你的原始资料通读、提炼、分类，写成一套结构化的 Markdown 维基页面，之后所有提问都基于这套页面回答。这份 Gist 在几天内拿到 5000 多 star，Cognition、Factory、LangChain、Garry Tan 四支团队几乎同步做出了工程实现。

它被说成「RAG 终结者」，本质原因只有一句：**它把做功的时机从查询端挪到了摄入端**。

传统 RAG 是查询时做功（compute at query time）：导入时只拆块、打向量，不思考；用户每问一次，就把「向量比对 → 召回片段 → 去重排序 → 拼上下文 → 当场推理」跑一遍。同一个问题问一百次，这套流程就完整跑一百次。

LLM Wiki 是摄入时编译（compile at ingest）：导入时让模型通读全文，理解、提炼、分主题写成页面；提问时只要定位到那一页，读进来就能答。

这是一个很朴素的转换：**把重复计算换成一次性产物**。缺点是产物会过时，所以它必须有第三条腿——定期校验。

背景与一手材料：
- [Where RAG Breaks Down: The Karpathy LLM Wiki Alternative](https://www.mindstudio.ai/blog/karpathy-llm-wiki-pattern-knowledge-base-without-rag) ⭐值得阅读
- [Karpathy 的原始 Gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- [卡帕西力推的 LLM Wiki，会淘汰传统 RAG 吗？](https://finance.sina.com.cn/tech/roll/2026-07-31/doc-iniktcvc4400385.shtml)

## 2. 传统 RAG 的成本结构：功夫全在提问那一秒（Query-time Cost）

RAG 的问题不在于「检索不准」这么简单，而在于它的**成本曲线形状**：固定投入极低，边际成本随提问次数线性增长。

导入侧几乎不花钱：一篇三千字的文档，切成十几个块，每块转成一个向量，存进向量数据库（vector database）。整个过程系统不理解内容，只是在做机械归档。

提问侧才开始烧钱，而且有四笔账同时记：

1. **嵌入成本**：问题也要转成向量；
2. **检索成本**：向量比对、召回 top-k（前 k 个最相似片段）、去重；
3. **上下文成本**：召回片段连同问题一起塞进模型；
4. **推理成本**：每次都要从原始片段现场推理出一个结论。

这四笔钱有一个共同特征：**答完就没了，不留任何痕迹**。第 100 次回答的质量，和第 1 次完全一样——系统不会因为回答过就变得更懂这份资料。用一句话概括就是：它在不停地重算同一道题。

更麻烦的是碎片化。切块（chunking）会切断语义：一个需要三段原文才能讲完整的结论，被切成三块之后，只要漏召回其中一段，模型就只能拿半截证据推理，却依然会自信地给出完整答案。

这里可以算一个条件概率，说明「漏片段」为什么是常态而不是意外。假设单块召回率为 $p = 0.9$，一条完整结论需要 3 个块同时命中，那么三段全中的概率是：

$$
P = p^{3} = 0.9^{3} = 0.729
$$

也就是说，即使每一块的召回率都有 90%，仍有 $1 - 0.729 = 27.1\%$ 的查询会缺至少一段原文。数字只随 $p$ 和段数变化，可以自己换成你项目的实际值复算。

在[长上下文时代，RAG 还有必要吗](https://juejin.cn/post/7666089320763523082)中我们讨论过长上下文对 RAG 的挤压：窗口变大只是让「塞更多碎片」变得可行，并没有解决「碎片本身不完整」这个结构问题。

## 3. LLM Wiki 是什么：三层架构与三个操作（Three Layers, Three Ops）

Mem0 在一篇行业综述里把这套系统整理成标准的三层结构，从上到下是这样：

| 层 | 内容 | 谁写 |
|---|---|---|
| 规则层 | `AGENTS.md` / `CLAUDE.md`：分类标准、更新规则、矛盾处理逻辑 | 人写，AI 遵守 |
| 维基层 | `wiki/*.md`：按主题成页，自带摘要、分类、语义内链 | AI 写、AI 维护 |
| 原始层 | `raw/`：论文、代码库、制度文档等原始素材 | 只读，不改 |

Karpathy 给过一个很到位的比喻 🧑‍💻：**Obsidian 是 IDE，LLM 是程序员，维基就是代码库**。人只负责提供素材和写规则，页面全部由 AI 编写与维护。

围绕这三层，系统只有三个操作：

- **摄入（ingest）**：来了新文档，模型通读后把信息合并进相关页面，同时更新内链；
- **查询（query）**：用户提问，先按页面标题、内链或轻量索引定位到具体页，再把整页作为上下文交给模型；
- **校验（lint）**：定期扫描全库，找出内容矛盾、信息过期、没有任何入口的孤岛页面，自动修正或标记。

三个操作里，前两个负责「写得快」，第三个负责「不至于写错还不自知」。少了校验，这套系统就会在半年内退化成一堆互相矛盾的文件——这正是人类维基失败的老路。

## 4. 本质区别：编译产物 vs 检索片段（Compiled vs Retrieved）

把两者放在同一张表里，差别一目了然：

| 维度 | 传统 RAG | LLM Wiki |
|---|---|---|
| 做功时机 | 查询时，每次重算 | 摄入时，只编译一次 |
| 最小单位 | 向量片段（几百 token） | 主题页（完整语义单元） |
| 跨文档关系 | 靠相似度临时拼接，无显式结构 | 显式内链，关系被写下来 |
| 人可读性 | 向量不可读 | Markdown 可读、可 diff、可 review |
| 成本曲线 | 随提问次数线性增长 | 前期一次性投入，之后近乎平坦 |
| 信息完整性 | 原文仍在，理论上可被召回 | 摘要会丢边缘细节，且不可逆 |
| 失效方式 | 召回不到就胡说 | 页面过期就整页胡说，且更有说服力 |

最后一行值得单独说。RAG 出错是「没找到」，表现是答非所问，用户容易察觉；Wiki 出错是「找到了，但内容是旧的」，而且排版整齐、结构清晰，反而更容易被当成权威采信。所以行业里有一句反常识结论：**错误的 Wiki 比没有 Wiki 更危险**。

## 5. 为什么现在才可行：80 年的维护成本被 AI 接走了（Maintenance Cost）

维基这个想法一点也不新。1945 年，范内瓦·布什就提出过 Memex 构想：一个能存下个人全部文档、并自动建立知识关联的系统。八十年过去，它一直没真正落地。

卡住的从来不是存储，也不是检索，而是**维护**。人类维基的日常是：更新页面、修正链接、同步信息、处理矛盾。这些活琐碎、没有即时反馈、不做也不会马上出事，于是团队一忙就搁置，内容慢慢过期，最后没人再用。

举个最常见的翻车现场：一份新人手册里，三处写着不同的报销额度，没人知道哪个是最新的，结果所有人都不看手册，直接去群里问。维基不是死于没人写，是死于没人维护。

大模型刚好补上这块短板：它不会倦怠、不会遗漏、不怕繁琐，一次操作能批量改十几个页面，还能按规则检查全库矛盾。第一次，「持续维护的结构化知识库」的运维成本降到了可以忽略。

这也是它跟「AI 记忆」最容易混淆的地方。要分清两层：**文档知识记忆**按主题组织，来自批量文档，所有人看到的一致；**用户交互记忆**按 user_id 组织，来自真实对话，记录偏好、决策、失败方案。Wiki 只做前者。指望搭一套维基就拥有「记住每个用户」的能力，是把两个数据模型混成了一件东西。

## 6. 一笔能算的账：编译成本多久能摊平（Break-even）

「更省」这个说法必须能算，否则就是感觉。下面这组假设可以整体替换成你自己的数字。

**假设**：知识库 100 篇文档，每篇 3000 字，约 2000 token（Token，模型处理文本的最小单位），平均每天 200 次提问。

**RAG 侧**：每次召回 5 个片段、每片约 400 token，单次上下文 2000 token。日成本：

$$
200 \times 2000 = 40\text{ 万 token/天}
$$

**Wiki 侧**：首次编译要通读全部原文并生成约 100 个页面。输入 100 × 2000 = 20 万 token，输出按每页 800 token 计约 8 万 token，合计约 **28 万 token**。日常查询只读 1 页，约 800 token。

单次节省是 $2000 - 800 = 1200$ token，日节省 $200 \times 1200 = 24$ 万 token。摊平周期：

$$
\frac{28\text{ 万}}{24\text{ 万/天}} \approx 1.2\text{ 天}
$$

也就是说，在这个提问频率下，编译成本一天多就回本，之后每天省下约 24 万 token 的重复计算。

但把提问频率换成每天 2 次，日节省只有 2400 token，摊平要 $\frac{28\text{ 万}}{2400} \approx 117$ 天；如果这 100 页里有一半从没被打开过，那部分就是纯粹的沉没成本——生成它们的 token 花掉了，收益为零。

所以「更省」有三个前提，缺一个就不成立：**文档相对稳定、查询频率足够高、页面确实会被读到**。这三条同时满足时，摄入时编译几乎是压倒性的；只要有一条不满足，RAG 的「按需付费」反而更划算。

## 7. 最小可跑实现：给维基做一次体检（Runnable Lint）

三个操作里，「摄入」和「查询」依赖模型，但「校验」是纯结构检查，一段脚本就能跑。下面这段零依赖，存成 `wiki_lint.py` 执行 `python wiki_lint.py` 即可，首次运行会自动生成一套示例维基。

```python
# wiki_lint.py —— LLM Wiki 的第三个操作「校验」，零依赖，python wiki_lint.py 直接运行
import re
import sys
from pathlib import Path

ROOT = Path(__file__).parent                      # 以脚本所在目录为维基根目录
RAW = ROOT / "raw"                                # 原始层：只读素材，用来判断新鲜度
WIKI = ROOT / "wiki"                              # 维基层：AI 生成的 Markdown 页面
LINK = re.compile(r"\[\[([^\]]+)\]\]")            # 语义内链写法 [[页面名]]


def ensure_demo():
    """首次运行时生成一套示例维基，保证脚本复制即跑"""
    if WIKI.exists():
        return                                        # 已存在就不覆盖，避免冲掉你的内容
    (RAW / "papers").mkdir(parents=True)              # 原始层目录
    WIKI.mkdir(parents=True)                          # 维基层目录
    (RAW / "papers" / "rag.md").write_text("# RAG\n按查询时检索。", encoding="utf-8")      # 一份原始素材
    (WIKI / "rag.md").write_text("# RAG\n见 [[llm-wiki]]。", encoding="utf-8")            # 正常互链的页面
    (WIKI / "llm-wiki.md").write_text("# LLM Wiki\n见 [[rag]] 与 [[broken-page]]。", encoding="utf-8")  # 含一条断链
    (WIKI / "orphan.md").write_text("# 孤岛页\n没人链接到我。", encoding="utf-8")          # 没有任何入口的页面


def load_pages():
    """读取所有维基页面，返回 {页面名: 正文}"""
    return {p.stem: p.read_text(encoding="utf-8") for p in WIKI.glob("*.md")}


def newest_raw_mtime():
    """取原始层里最新的修改时间，作为「新鲜度基准」"""
    stamps = [f.stat().st_mtime for f in RAW.rglob("*") if f.is_file()]
    return max(stamps, default=0)


def lint():
    """做三项检查：断链、孤岛、过期，返回问题列表"""
    pages = load_pages()                              # 全部页面
    base = newest_raw_mtime()                         # 新鲜度基准
    linked = set()                                    # 被链接过的页面名
    problems = []

    for name, body in pages.items():                  # 逐页扫描内链
        for target in LINK.findall(body):             # 抽出 [[...]] 里的目标
            linked.add(target)                        # 记录「有人指向它」
            if target not in pages:                   # 目标页不存在 → 断链
                problems.append(("断链", f"{name} -> {target}"))

    for name, path in ((p.stem, p) for p in WIKI.glob("*.md")):  # 逐页检查孤岛与过期
        if name not in linked and len(pages) > 1:                # 没有任何页面指向它
            problems.append(("孤岛", name))
        if path.stat().st_mtime < base:                          # 比最新素材还旧 → 可能过期
            problems.append(("过期", name))
    return problems


def main():
    """打印体检报告，有问题时以非零状态码退出，方便接进 CI"""
    ensure_demo()
    problems = lint()
    if not problems:
        print("wiki 健康：无断链、无孤岛、无过期页面")
        return
    for kind, detail in problems:                     # 逐条输出，便于直接修
        print(f"[{kind}] {detail}")
    sys.exit(1)                                       # 有问题的库不让流水线通过


if __name__ == "__main__":
    main()
```

跑完你会看到三类问题被点名：`llm-wiki` 指向了不存在的 `broken-page`；`orphan` 没有任何入口；`orphan` 还比最新素材旧。这三项恰好对应维基退化的三个方向——**关系断掉、内容孤立、信息过期**。

把它接进 CI 或每日定时任务，就是 Factory 那条「代码一提交就重建维基」思路的最小版本：不靠人的自觉性维护，靠工程机制保证知识库不腐烂。

内链的价值也不止于好看。它本质上是一份**目录索引**：AI 先读索引，再按链接定点取页，就不需要通读全库——这和「给每个文件夹放一份 README 让 AI 先读」是同一套取件逻辑，只是搬到了知识层。

## 8. 症状 → 原因 → 解法对照表（Symptom Table）

| 症状 | 原因 | 解法 |
|---|---|---|
| 同一个问题问三次，三次答案细节不一致 | 查询时做功，每次召回片段不同 | 高频问题编译成固定页面，答案口径统一 |
| 答得挺流畅，但只答了一半 | 完整结论被切块切断，漏召回中间那段 | 以主题页为单位组织，一页装完整语义单元 |
| 新增文档后，回答问题开始自相矛盾 | 新旧内容没有合并，页面之间没人对账 | 摄入时更新既有页面，并用 lint 查矛盾 |
| 知识库越用越没人看 | 页面过期无人维护，读一次错一次 | 把校验自动化，接进 CI 或定时任务 |
| 检索系统运维成本比收益还高 | 文档量还没到需要向量库的规模 | 百级信息源先用 Markdown + 索引，别硬上基础设施 |
| 以为 Wiki 能记住每个用户偏好 | 混淆文档知识记忆与用户交互记忆 | 文档归 Wiki，用户偏好归独立的记忆层 |
| 编译了一堆页面，几乎没人打开 | 摄入成本前置，但访问频率太低 | 先按访问日志筛主题再编译，别全量预生成 |

## 9. 四个绕不开的边界（Limits）

**边界一：规模上限。** Karpathy 自己给了阈值——约 100 个信息源、几百个页面。超过之后，页面之间的关联会变得庞杂，增量更新和全量校验的成本急剧上升，纯导航不够用，必须补 BM25（稀疏关键词检索）+ 向量检索 + LLM 重排序（rerank，重排）。

**边界二：精度损失。** 摘要一定丢边缘细节，而丢掉的东西后续所有查询都找不回来。RAG 重复成本高，但原文还在，理论上仍有被召回的机会。这是「用完整性换效率」的经典权衡，没有免费的版本。

**边界三：时效风险。** Wiki 的准确度等于最后一次更新的准确度。四家实现里只有 Factory 做成了 CI 自动重建，其余三家都要人工执行命令刷新——它们的知识库质量，取决于上一次手动更新是什么时候。

**边界四：沉没成本。** 提前做功不是免费，只是把账单从查询侧挪到了摄入侧。生成页面要 token，校验清理要 token，而那些从未被访问的页面，成本是 100% 浪费。文档体量大但查询频率低时，Wiki 可能比 RAG 更贵。

再加上一条认知边界：Wiki 管「资料里写了什么」，不管「这个用户上次要什么」。前者按主题组织，后者按用户组织，数据模型完全不同，别指望一套解决两个问题。

## 10. 判据：什么该编译，什么该检索（Verdict）

**该走 Wiki（摄入时编译）**：

- 资料相对稳定，几个月才更新一批；
- 同一批问题被反复问，频率高；
- 需要结构化答案，读者要看到「全貌」而不是零散片段；
- 规模在百级信息源以内，不想维护向量基础设施。

**该走 RAG（查询时检索）**：

- 文档量早已超过几百页，且还在持续增长；
- 查询长尾、低频、每次都不一样；
- 对细节精度要求高，不能接受摘要丢信息；
- 需要按用户或部门做细粒度权限隔离——原文级检索天然更好控。

**混合是主流答案**：核心、高频、稳定的知识预编译成页面，长尾、低频、细节性问题仍走检索。判断标准只有一条——**这份知识会被问多少次**。问得多的，编译一次摊薄；问得少的，按需去查。

资料稳定、提问高频、规模在百级信息源以内时，先用 Markdown 维基，别急着上向量库；文档量大、查询长尾、细节精度要求高时，RAG 仍是更稳的选择，别为了追新把检索拆掉。

本专栏《RAG 技术专栏》从数据预处理、文本分块、Embedding 与向量检索一路讲到重排序、上下文组装与知识库选型，每篇配一段可直接运行的代码和一张症状对照表，每周更新一篇。想按顺序读完，可在专栏页订阅。
