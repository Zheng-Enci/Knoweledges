# 发布到抖音（publish-douyin）

> 👉 **触发方式**：可由用户说「发布最新文档到抖音 / 发布到抖音 / 发抖音 / douyin」等关键词**独立触发**；也可由 `publish-latest-doc` command 第 0️⃣ 步用户选定「抖音」时，由 command 引导读取本 skill。两种方式都会执行本 skill。

## 📌 通道铁律（强制）

| 项 | 要求 |
|---|---|
| **必须使用通道** | **chrome-devtools MCP**（`chrome-devtools_navigate_page` / `chrome-devtools_evaluate_script` / `chrome-devtools_click` 等） |
| **禁止通道** | TRAE 内置沙盒浏览器（chrome 插件通道，`browser_tabs` 系列，即 TRAE Browser Control） |
| **原因** | 抖音图文卡片上传、选曲、正文注入均依赖 `evaluate_script` 与隔离 profile；走 chrome 插件通道易致注入失效或登录位不一致。两套通道互斥，严禁混用。 |

> 🏷️ **通道术语对照**：用户口中的「TRAE 内置沙盒浏览器」= TRAE Browser Control / chrome 插件通道（`browser_tabs` 系列）。它与 chrome-devtools MCP 是**两套互斥通道**。抖音走后者。

> ⚠️ **发布形态（2026-10 改版后）**：网页端只剩「发布视频」与「发布图文」两个入口，**没有纯文字作品**（文字模式仅在 App 端提供）。描述框虽标 1000 字上限，但编辑器是 ProseMirror（`editor-kit`），长文本写入会回滚、清空后模型不同步。因此抖音一律走「正文做图」：把 `-抖音.md` 的 `P01…PN` 各页原样转成竖版卡片图，按**图文作品**发布，描述只留短摘要 + 话题。

> 🔒 **发布时文字零改动**：卡片文字必须与 `-抖音.md` 对应页**逐字一致**，不增删改任何文字、不重写、不润色、不调顺序。允许的处理只有排版类——**加粗**关键句、**着色/高亮**关键数字、分页、断行、把表格转成图表版式。需要改文字就回文档改，不在发布环节改。

## 🧩 共用前置流程（先执行，再进发布）

以下为三平台共用步骤，抖音 skill **各自内联**一份，执行时按序走完。

### P1 定位最新文章组（Document Group）

在项目根目录执行（Git Bash）：

```bash
find . -name "*.md" \
  -not -path "./.trae/*" \
  -not -path "./.git/*" \
  -not -path "*/resources/*" \
  -not -name "README.md" \
  -not -name "*url链接目录*" \
  -not -name "*目录.md" \
  -not -name "*-知乎.md" \
  -not -name "*-腾讯云.md" \
  -not -name "*-小红书.md" \
  -not -name "*-抖音.md" \
  -printf "%T@ %TY-%Tm-%Td %TH:%TM %p\n" \
  | sort -rn | head -n 5
```

- 🥇 取**母稿 mtime 最新**的一篇作为本轮发布对象，输出前 5 名候选及时间，报告最终选中项及理由。
- ⚠️ **秒级排序精度不足**：`%T@` 是秒级时间戳，批量产出时多篇同秒落盘。**必须在秒级之上做毫秒级二次判定**：对秒级结果中 mtime 相邻（同秒或差 <1s）的候选，用毫秒级 mtime（`find -printf "%T@ %TY-%Tm-%Td %TH:%TM:%TS"` 或 `stat -c %y` / `Get-Date` / `LastWriteTime`）精确比对，取**毫秒级最新**为一篇为母稿，其余同秒候选不作并列。报告附候选毫秒级时间。
- 🎯 **「最新且未发布」判据（强制）**：`find` 只按 mtime 倒序，不判断是否已发布。拿到前 5 名后须叠加「未发布」过滤——逐篇检查对应专栏 `00-*链接目录.md`，若该篇标题已在链接目录出现（掘金 / CSDN / 抖音任一平台记录）即视为已发布，跳过并标注。取 mtime 最新且未发布的一篇；前 5 名全已发布则顺延到前 10 名再判。⚠️ 过滤依据是**标题**匹配链接目录，不是文件序号。
- 🧩 由母稿路径推导整组 2 个文件，缺项直接标「未生成」：

| 产出 | 路径规则 | 发布平台 |
|---|---|---|
| 母稿 | 定位结果 | 掘金 + CSDN |
| 变体 | `{母稿去扩展名}-抖音.md` | 抖音 |

- 🚫 排除项：`.trae/`、`resources/`、`README.md`、各类 `url链接目录`、临时草稿与 `.rendered.html`。
- 🗂️ `*-知乎.md`、`*-小红书.md`、`*-腾讯云.md` 为历史遗留变体，已停止生成与发布，保留在 `find` 排除列表防止被误当母稿。
- ⚠️ **绝不允许**把变体文件当母稿发到掘金 / CSDN：变体按平台分发，母稿只走长文双平台。抖音只发 `-抖音.md` 变体。

### P2 解析标题、专栏与 front-matter

| 字段 | 母稿 | 变体 |
|------|------|------|
| **文章标题** | 文件名去扩展名 + 去编号前缀 | front-matter `title` |
| **摘要** | 按 P5 重写 | front-matter `summary`，仅按平台上限压缩 |
| **标签** | 正文 + 文件夹名提取 | front-matter `tags` |
| **专栏名** | 文档所在**文件夹名**（原样保留） | 同上（**抖音无专栏，落成话题**） |

- 🔢 编号前缀正则：`^[A-Za-z]{0,4}[0-9]+[A-Za-z0-9]{0,6}[-_ ]+`
- 🧪 对照示例：
  - `A04-AI时代什么样的程序员不会被淘汰-抖音.md` → 标题取 `title` 字段，文件名编号不进平台标题
  - `J1C-IDE选择与使用-...` → `IDE选择与使用-...`
  - `09aaa-LayerNorm是什么？` → `LayerNorm是什么？`
  - `@Bean注解基础入门-...` → 无编号，保持不变
- 🔗 **串台校验**：变体 front-matter 的 `source` 必须等于本组母稿完整文件名；不一致即视为串台，停止发布并在汇报里标注。
- 🏷️ 标签建议：抖音**无专栏**，标签落成话题（≤5 个），取自 front-matter `tags`。
- 🚫 抖音标题严格控制在 20 字内、摘要控制在 30 字内（front-matter 已按此写）。

### P3 生成封面图（两种比例）

刷信息流时用户只能看到三样东西：**标题、摘要、封面图**。两种比例各自独立生成，不能一张横图裁两个平台。

| 用途 | 尺寸 | 落盘路径 | 适用平台 |
|---|---|---|---|
| 横版 | `2560x1440`（16:9） | `Temp/<语义化主题>_2560x1440.png` | 掘金、CSDN |
| 竖版 3:4 | `1080x1440` | `resources/{文档编号}/douyin/photo/P01.png`（`P01` 兼封面，见发布步骤） | 抖音图文卡片 |

> ⚠️ **抖音卡片直接落位**：抖音图文卡片（`P01…PN`）从生成那刻起就**直接写入 `resources/{文档编号}/douyin/photo/`**，不经 `Temp/` 中转；卡片生成脚本写入 `resources/{文档编号}/douyin/code/`。见 `.trae/rules/文档外部资源存放规范.md`。

**做法**：调用全局 `/生成图片` 指令（绝对路径 `C:\Users\zheng\.trae-cn\commands\生成图片.md`，不在本项目内）生成横版 `2560x1440`，默认不加水印；竖版卡片用 `card_gen_html.py` 一键生成（见发布步骤 7.1）。

> ⏩ **提速：封面并发生成**（必做）：若需同时生成横版与竖版，用 `min(2,3)` 多线程并发生成，不要串行等两张。

**🖥️ 本机 Python 环境（需要代码绘制图片时用）** 🔒：

| 项 | 值 |
|---|---|
| 解释器 | `C:\Users\zheng\OneDrive\Desktop\CodeEnvironment\miniconda3\python.exe` |
| 版本 | Python 3.14.7（Anaconda 打包版） |

**吸引力公式（按优先级）** 🔥：

1. **夸张情绪的主体**：一张脸或一个拟人化主体占画布 **15% 以上**，表情夸张的惊讶、崩溃或得意——缩到 200px 时只有极端表情还看得清。带人脸的封面实测点击率高出约 38%。
2. **眼神引流**：主体视线指向标题文字或画面冲突点。
3. **高对比撞色**：主体与背景用互补色，优先 **黄+黑**、红+白；整体「背景 80% 收敛、主体 20% 高饱和」。
4. **给结果、藏方法（悬念）**：画面只呈现冲突的结果，不给出解法。
5. **文字要大，字少字大**：横版主标题 **5–7 个字、字号 ≥ 画布宽的 1/10**；副标题／数字 **字号 ≥ 画布宽的 1/18**；全图文字总量 ≤ 20 字。竖版最多 5 个字，字号 ≥ 画布宽的 1/8。粗黑体，且不与文章标题重复。
6. **三元素上限**：主体 + 一个对比物 + 一行字，再多就糊成一团。

**必须贴合文档** 🎯：视觉隐喻直接取自本文核心冲突；图上文字只能来自标题或其同义改写，禁止出现文档里没有的数字、百分比、性能指标；禁止真实人物肖像、平台 logo、二维码、水印。

**落地检查** ✅：

- **横版按 350 px 宽自查**：主标题折合字高 ≥ `35 px`、副标题 ≥ `19 px`；看不清就放大字号或砍字后重出图。
- **🖼️ 文字测宽铁律（生成封面脚本必守）** 🔒：
  - **禁止固定 x 坐标 + 固定字号放文字**：必须先测量文字实际渲染宽度再决定字号与起点。
  - **必须用 `textlength` / `textbbox` 动态测量**：用 `fit_font(text, max_w, start_size, max_size)` 递归缩放字号直到宽度 ≤ `max_w`；起点 `x` 由「区域起点」而非「固定像素」决定。
  - **主标题字号有上限也要自动收缩**：即使写 `max_size=300`，测宽超 `right_max_w` 也要降字号回退（步长 4px），保证任何文本不超出画布右缘。`right_x` 取「左侧主视觉右缘 + 安全间距」，并反算 `right_max_w = 画布宽 - right_x - 右侧安全边距`。

### P4 生成发布稿（不改原文档）

在临时目录为**每个待发布产出各生成一份发布副本**，原文档**只读不写** 🔒

1. **🧾 剥离 front-matter**：变体首部 `---` 包裹的整段 YAML 必须删除（母稿无 front-matter，本步跳过）。
2. **✂️ 去掉正文首个一级标题**：若正文首行是 `# 与标题相同/相近的 H1`，删除该行。
3. **🖼️ 本地图片转 GitCode Raw URL**：按 `.trae/rules/GitCode图片URL转换规范.md` 转换（抖音变体如有图片时适用）。
4. **🧾 其余内容原样保留**：不润色、不删改段落、不调整结构 🚫
5. **📵 抖音额外做纯文本化**（本平台不渲染 Markdown）：
   - 删掉 `**`、`##`、`>`、行内反引号，把标题降级成口语分段
   - 段间保留空行，避免挤成一坨
   - 话题统一写成 `#标签`，追加在正文末尾，取自 front-matter `tags`
   - 抖音标题取 front-matter `title`，正文直接用纯文本版
   - 但实际发布走「正文做图」（见第 7️⃣ 节）：纯文本版仅作为描述（≤200 字）+ 话题素材，正文按页转卡片图

### P5 平台摘要撰写（必做，禁止用平台自动提取）

抖音**描述**（≤200 字）**必须手动改写**，不能保留平台自动提取的内容，也不把全文塞进描述。

**分工** 🔀：**变体**直接用 front-matter `summary`（已是按平台改写的手写稿），只需按平台上限压到 ≤200 字；**不得替换成平台自动提取内容**。

**写作规则** 🔥：

1. **开头 15 字内抛痛点或反常识结论**：不用「本文介绍了」「随着……的发展」这类开场
2. **中段给具体交付物**：几个关键数字、能解决什么问题
3. **结尾留一个具体钩子**：一句引导回复的话
4. **末尾追加 `#标签` 话题**（≤5 个，取自 front-matter `tags`）
5. **禁止**：编造数据、夸大承诺、「史上最全」「干货满满」「包过」「一键搞定」
6. **禁止直接复制正文首段**：描述要能脱离正文独立阅读

**模板** 🧩：

```
{痛点或反常识结论}：{具体做法 + 关键数字}。{读者能拿走什么}，{留一个钩子}。#话题
```

### P6 图片可获取性预检（重点，发布前必做）⚠️

GitCode Raw 图片首次访问可能空白或返回占位图，**发布前必须逐个验证每个图片 URL 能否真正取到**，不能默认可用：

1. 从发布稿抽出**全部** GitCode 图片 URL，整理成清单。
2. 在浏览器**新标签页逐个打开**每个 URL，等待图片真正加载完成（必要时**手动点击/刷新一次**触发 GitCode 回源）。
3. 按结果分流：
   - **(a) 能取到** ✅：继续下一个。
   - **(b) 取不到**（空白 / 占位 / 404）🔧：先判断该图**是否需重新上传**——
     - 本地有源文件、链接确实失效 → 重新上传覆盖原文件并 `git push`（资源上传允许自动 push），再回第 2 步复验；
     - 不需重传（文件已在仓库、只是未回源）→ 去 GitCode 仓库对应文件页**手动点击**一次触发回源，再复验该 URL。
4. 回到编辑器，刷新预览或重新粘贴该图片，确认编辑器内**图片可见**。
5. ✅ 全部图片确认可获取后才允许进入发布提交；任一图始终取不到，用仓库 blob 页 URL 或改本地直传兜底。

### P7 配套资源链接预热（重点）⚠️

正文里的「📦 配套资源」直链（`.py` / `.java` / `.sql` / `.zip` / `.json` 等**非图片**文件）指向 `raw.gitcode.com`。该域名是 CDN，仓库文件首次被访问时可能返回 404、空白或占位内容——只有先在浏览器里真实走到该文件、触发一次回源，raw URL 才会稳定可下载。

**触发条件**：发布稿中存在 `https://raw.gitcode.com/...` 且后缀不是图片的链接，或正文出现 `> 📦 配套资源：` 行。命中即必须执行。母稿命中即视为全组命中，只需预热一次。

**做法** 🔧：

1. **列出清单**：从发布稿中抽出全部资源 URL，逐个 URL decode 得到仓库相对路径，整理成「URL → 相对路径」对照表
2. **进仓库首页**：`navigate_page` 打开 `https://gitcode.com/ZhengEnCi/knoweledges`，`take_snapshot` 确认页面正常渲染（不是 404、不是登录墙）
3. **模拟人工点击**：在文件树里**逐级点击**目录，最后点击目标文件名进入 blob 页面（必须真的点开每一级目录和文件，不能只改地址栏直达）
4. **确认文件内容**：blob 页面渲染出真实源码（能看到首行代码），而不是「文件不存在」提示
5. **再点 Raw**：点击「原始数据 / Raw」按钮打开 raw 页面，确认返回的是**纯文本源码**
6. **刷新校验**：在该 raw 标签页 `navigate_page` 重新加载一次，仍能拿到内容，才算预热成功
7. **逐个复测**：对清单里每个资源 URL 重复第 2–6 步，全部通过后才允许进入发布
8. **兜底替换**：若某条 raw 链接重试 2 次仍 404 或空白，改用仓库 blob 页面 URL 替换正文该处链接，并在汇报里注明
9. **回写发布稿**：预热过程只允许调整链接形式，**不得改写资源名称、说明文字、所在段落** 🚫

## 7.1 卡片图规格 📐

| 项 | 要求 |
|---|---|
| 尺寸 | **`1080x1440`（3:4 竖版）**，全部卡片同一尺寸，避免平台混排裁切 |
| 张数 | 等于文档分页数 N：`P01…PN` 一页一卡，**不得合并、拆分、增删或改序**；`P01` 兼封面，`PN` 给结论 |

### 7.1.0 卡内排版细则（垂直分布与字距）📐

**① 垂直分布（Vertical Layout）**：内容块**垂直居中**，上下留白均衡，既不上顶也不下坠：

- **垂直居中**：整组内容（标题 + 正文 + 数字）的中心点落在画布**垂直中轴线附近**（建议中心 `y=48%–50%`，即内容总高占画布 `50%–60%` 时居中放置），**上下留白尽量相等**
- **上下对称留白**：内容上方留白与下方留白之差 ≤ 画布高度 `3%`（约 `40px`，以 `1080x1440` 计）；不做「重心偏下」，那会让内容堆到卡片下半部、上半部空旷
- **内容上边距**：不要从 `y=0` 顶格画；顶部留白至少 `画布 12%`，若内容较矮（总高不足画布 `50%`）则自动增大上下边距把内容撑到居中，底部不贴边
- **内容不足自动撑满**：若排版后正文 + 标题总高不足画布 `55%`（画面下半大片留黑），**先把字号 / 行距 / 段距按比例放大**（正文字号可到 `54–64px`、行高 ×1.6–1.8），把主体撑到画布 `60%–75%`，再居中；**不得把碎文字硬堆在画布上带一片空黑**
- **视觉骨架（Structure Visuals）**：每条 bullet 前加序号 `①②③` 或绿色实心点 + 竖线，重点页用分组色块 / 进度条 / 数据块承载核心数字；**让每条 bullet 之间有清晰的层级关系**（并列冒号对齐、递进用箭头 `→`），观众扫一眼能读出「这页几条、哪条最重」
- **留白区（Padding）**：左、右 padding 均 ≥ `120px`，底部 padding ≥ `160px`；要避免卡片底部贴边被平台裁切
- **⚠️ 右侧安全区（Right Safe Area）**：抖音 feed 页面**右侧约 `1/7` 宽度**被头像、点赞、收藏、评论、转发等互动按钮占据，会覆盖卡片右缘。因此**正文与关键元素（标题、数字、色块）不得进入右侧 `> 画布宽 85%` 的区域**；即右侧留白应在 `120px` 基础上再加大到 ≥ `画布宽 × 15%`（约 `160px`，以 `1080x1440` 计），**核心文案整体左移**，预留右侧遮挡空间，避免「字被按钮吃掉」。
- **⚠️ 文案不出屏（Atem Edge Safety）**：所有文字（标题、正文、数字、色块）的**完整外边界**都必须落在画布 `x ∈ [0, 画布宽]` 且 `y ∈ [0, 画布高]` 之内，**任何一字、一符号不得溢出画布边缘**。抖音 App / 网页预览的**可视区域比剪裁图更窄**：卡片生成时是按整张 `1080x1440` 画，但**手机端首屏往往只显示中间一段**，上下与左右两端都可能被裁或缩到屏幕外。因此**不能只按画布尺寸居中就算合格**，必须额外做「手机可视区」校验：把实际渲染内容整体缩到 `画布宽 × 85%`、`画布高 × 78%` 的**内缩安全框**内再检查一遍，确认**全部文字落在这个内缩框里**。超框就**整体缩小字号 / 增大边距 / 精简行数**，而不是靠贴边硬排。判据：最右文字右缘 ≤ `画布宽 × 92%`，最左文字左缘 ≥ `画布宽 × 8%`，最下文字下缘 ≤ `画布高 × 92%`，最上文字上缘 ≥ `画布高 × 8%`。**实测踩坑**：曾出现封面页标题等文字贴到卡片右缘 / 底部，手机端直接看不到——即本条的由来，务必逐卡自查。

**② 字距与行距（Letter & Line Spacing）**：大字与相邻字挤在一起，是因为字号大但行高/字距没同步放大 🔧

- **行高（Line Height）**：正文行高 = `字号 × 1.5–1.8`；标题行高 = `字号 × 1.15–1.3`；**字号越大行高倍数越要往高取**，避免两行大字粘在一起
- **段间距（Paragraph Gap）**：标题与首段正文间距 = `字号 × 0.8–1.2`（或 ≥ 40px），段落之间 ≥ `30px`；标题、数字、正文三类元素之间强制留出**区隔空白**
- **字距（Letter Spacing）**：大字（标题 / 核心数字）字距设为 `字号 × 0.03–0.06`，中小字 `0`；字距太小会让笔画粘连
- **文字内边距（Padding around text）**：高亮数字或结论词做色块时，色块内边距 = `字号 × 0.15–0.25`，且色块与前后文字的**最小间距 ≥ 20px**，防止高亮词紧贴相邻词
- **防重叠校验**：`Pillow` 画完每行后，用 `textbbox`/`measure` 实测各行边界，若任意两行/两词的 `bbox` 纵向或横向**间距 < 8px**，则增大行高或字距后重画，不得硬挤

**③ 一行放不下的处理**：大字（尤其标题 / 核心数字）超过画布可用宽度 `90%` 时，**按词断行、增大行高**，不靠缩小字号硬塞；断行后每行仍满足字距规则 ✅

**生成方式**：用本机 Python + Pillow 绘制（解释器路径见 P3），字体 `msyh.ttc` + `consola.ttf`；也可用 Playwright 截 HTML。脚本用完即删，不在项目目录留 `.py`。⚠️ 脚本只做**排版**：文字从对应页原样读取，禁止在脚本里重写、精简或补写文案。**排版必须落地 7.1.0 细则**：内容垂直居中、上下留白均衡、字号与行距字距成比例、高亮色块与相邻文字留足间距、画完校验 `bbox` 无重叠；**生成后逐卡自查「文案不出屏（Atem Edge Safety）」**（最右 / 最左 / 最下 / 最上文字缘分别落在画布宽 `92% / 8%` 与画布高 `92% / 8%` 内），并在 `P01` 重点核对「**画面里不得出现『封面』二字**」。

### 7.1.1 封面专项自检 ✅（`P01` 兼封面，逐条打勾）

抖音 feed 里封面只以约 **200px 宽**出现，`P01` 的设计目标是「让人停下来」，不是「把这一页的信息排完」。设计目标是**钩子**，不是**目录**。

| # | 检查项 | 判据（可复算） | 不通过怎么办 |
|---|---|---|---|
| 1 | 200px 缩略可读 | 把 `P01` 缩到 200px 宽另存 `Temp/publish/cover_check.png`（仅自检用临时图），仍能读出**一个冲突 + 一个数字** | 只改版式重出，不动文字 |
| 2 | 主视觉占比 ≥30% | 画布上至少有一个元素（超大数字 / 拟人主体 / 图形组）面积占整图 ≥30%，且其字号或边长 ≥ 画布宽的 1/5 | 放大主视觉，压掉次要元素 |
| 3 | 痛点短语 ≤9 字 | 封面上除标题外另有一句 ≤9 字的冲突短语（如「改一处，动十八处」），**只能由该页已有文字截取或同义重组**，禁止新造数字与概念 | 从标题句里截；截不出说明标题句本身不够锋利，回文档改 |
| 4 | 撞色对比 | 主色与底色明度差 ≥60%；强调色**必须与全组一致**（深底 `#0B0D12` + 绿色 `#22C55E`），高亮数字可用亮黄 `#FFD400` 点缀但不得整卡另起色系 | 换强调色，但不得跳出全组色板 |
| 5 | 对比可量化 | 两个数字不能只并排：必须用砖块 / 进度条 / 面积差把倍数关系画出来（18 vs 4 要一眼看出是 4 倍多） | 补可视化元素 |
| 6 | 双方案择优 | 每次至少出 **2 个构图不同**的封面方案，按 1–5 打分取高分者，另一方案不发布 | — |
| 7 | 封面页不出现「封面」字样 | `P01` 是**封面图**（功能定位），但**画面里不得出现「封面」二字**，也不得出现「封面图 / Cover / 主图」等任何标注性文字；封面只承载标题、冲突短语、数字这些**内容**，不出现关于「我是封面」的说明 | 删掉该词，用内容表达；若该词来自文档原文，回文档改，不在发布环节删 |

**铁律** 🔒：任一条 ❌ 不得进入发布步骤第 2 步上传。`P01` 与其余卡片同一尺寸同一风格，但自检口径按本表执行。

## 7.2.1 发布后必做：发布一条钩子评论（适用掘金/CSDN/抖音）💬

**发布即评论** 🔒：本规则对**掘金、CSDN、抖音**三个平台统一适用，落在**发布动作完成的下一瞬间**走——**不等文章审核通过、不等发布确认**，点完「发布」立刻进入刚发布的文章/作品，用作者账号发一条钩子评论。（评论置顶视平台能力而定，**不需要强制置顶**，钩子评论能上墙即可。）

> 🤖 **全自动执行**：发布钩子评论是发布流程的**固定收尾步骤**，AI 自行进入作品详情页、发布钩子评论，**不需要向用户询问是否同意、也不需要等用户确认**。默认用户已授权。仅当出现平台验证（扫码/短信）等必须人工介入的环节时，才停下来请用户协助。

**内容要求**（在「互动钩子」5 点基础上，补充一个**新角度**）：

| 要点 | 要求 | 示例 |
|---|---|---|
| 补一个新角度 | 给正文没展开的一个新判断或新数据 | 「我审 AI 代码最怕的不是语法错，是逻辑很『对』但根本不是业务要的」 |
| A/B 选项 | 给出两个明确可选答案 | 「A 遇到过 B 没踩过」 |
| 一句引导 | 用一句话鼓动回复 | 「你遇到过吗？评论区聊聊」 |
| 呼应正文 | 钩子要与文章核心判断一致 | 与标题/末页钩子口径对得上 |

**默认策略（无需手写）** 🤖：钩子疑问句由 AI **从正文核心冲突自动生成**——抓取全文最具争议的二元对立点，写成一句「具体经历 + A/B 选项 + 一句能回」的开放疑问。生成后无需用户确认，直接作为发布即评的钩子文案；若正文末页已有强烈钩子，可围绕它换一个角度改写，避免与末页原句重复。

**发布评论流程**：
1. 进入刚发布的作品详情页，点「评论」
2. 编辑评论，粘贴准备好的钩子文案（含一个新角度 + A/B 选项）
3. 提交，校验钩子评论成功上墙（评论区出现该评论、带作者标识）
4. 若平台支持且入口可用，可顺手置顶；不支持或不方便则跳过，**不强制**

**发布后 24 小时跟进**：有新评论就**及时回复**（越快越好），避免评论冷场拖累互动率；回复也尽量给判断而非敷衍。

## 7.3 背景音乐选曲规范 🎵

抖音图文**强制配乐**：没有 BGM 的作品完播与推荐都吃亏，且发布后无法补（见问题库第 21 条）。选曲不是凭感觉，按下面六步走。

**第 0 步 · 风格硬拦截（最高优先，先于一切）** 🔒：

- 选曲**只允许从「推荐 / 热门榜 / 纯音乐」三个分类取**，**禁止进入「伤感」「流行」「DJ」「搞笑」分类**；面板分类栏里有「伤感」入口，**不得点它**。
- 每个曲目必须过一遍第三步硬指标：**含哭腔、悲情、伤感古风、燃爆、强人声的曲目，无论多热门一律禁用**。知识类图文默认「冷静说理」调性，配伤感/BGM 与结论打架，属于情绪错配。
- 选完必须用「曲名 + 时长 + 风格方向」做最终复核，确认与文档调性映射表一致；风格方向偏「情歌 / 古风 / 伤感」的，即使已点「使用」也要返回重换。

**第一步 · 判断文档调性**：看标题与正文的「表达目的」，不是看所属技术领域。

| 文档调性 | 判定信号 | 风格方向 | 优先入口 |
|---|---|---|---|
| 知识科普 / 技术拆解 / 数据实测 | 大量数字、对照表、代码、结论型标题 | Lo-Fi Hip Hop、Chill Beats、轻音乐（纯器乐），BPM 80–90 | 推荐、热门榜，搜 `lofi` / `chill` / `纯音乐` |
| 方法论 / 效率 / 职场观点 | 清单、判断句、经验总结 | 轻快电子、Corporate、钢琴轻流行 | 推荐、流行 |
| 个人叙事 / 经历复盘 | 第一人称、时间线、故事 | 舒缓钢琴、Acoustic | 推荐 |
| 踩坑 / 反差实测 | 强对比、警示、推翻常识 | 轻节奏鼓点、Future Bass（无人声） | 热门榜、卡点（只取器乐） |

**第二步 · 联网确认风格**：对映射表选出的风格名先搜一轮，确认它是不是「纯器乐 + 情绪中性」，避免被名字误导（如「卡点」分类里大量带人声说唱）。搜索只用于定方向，最终仍回平台榜单选曲。

**第三步 · 硬指标逐条打勾**（任一条不满足就换曲）：

- **纯器乐、无歌词人声**：有人声会抢注意力，知识类作品尤其伤完播
- **BPM 80–90**，知识类不超 110；强鼓点卡点会让「冷静说理」的调性失真
- **情绪中性**：不哭腔、不悲情、不燃爆；讲「成本下降」「效率提升」却配伤感古风，属于情绪与结论打架
- **时长 ≥ 作品时长**，不足 60 秒的曲目直接跳过（图文轮播 5 张通常要 1 分钟左右）
- **优先使用人数高的曲目**：推荐 / 热门榜前列，平台分发更稳；冷门曲目可能触发版权或静音

**第四步 · 操作路径**（细节与踩坑见问题库第 19、20、22、27 条）：

1. 图片全部上传后，点入口真身 `span.action-Q1y01k`（父容器 `div.container-JngpiB` 点不动）
2. 面板分类：推荐 / 热门榜 / 收藏 / 飙升榜 / 原创榜 / 卡点 / 纯音乐 / 旅行 / DJ / 搞笑 / 流行 / 伤感 —— **按第 0 步只进「推荐 / 热门榜 / 纯音乐」；「伤感 / 流行 / DJ / 搞笑」禁用（可点「卡点」但只取器乐，不取带人声的）**
3. 需要搜索时，向 `input[placeholder="搜索音乐"]` 用原生 value setter 写值并派发 `input` 事件
4. 匹配到曲目后，点该行应用按钮（类名可能为 `button.apply-btn-LUPP0D` 或 `div.card-wrapper-*` 内文本为「使用」的叶子节点）；**点行本身只切试听，不会选中**

**第五步 · 校验（唯一真值）**：发布页「扩展信息 → 选择音乐」区域变成「曲名 + 时长 + 修改音乐」。没出现这段文案就是没选中，**禁止点「发布」**。

**禁区**：强人声 / 说唱、伤感古风与哭腔、燃系卡点、带剧情音效（笑声、警报、爆炸）、与结论情绪相反的曲目。

**已发布作品无法补配乐**：网页端「编辑作品」页没有音乐模块，只能删除后重发。

## 7.4 已知失败路径 🚫

- **描述框被污染**（内容重复堆叠、计数器卡在 `1000 / 1000`）后不要原地抢救：`execCommand('delete')`、合成 `KeyboardEvent`（Ctrl+A / Ctrl+Z）、`browser_type({clear:true})` 都只改 DOM，PM 模型仍是旧文本 → 关掉该 tab、新建 tab 重开 `content/post/image`
- **「暂存离开」** 后草稿不进「内容管理」列表（该页只有「作品」tab），只能从发布页弹窗「继续编辑」恢复
- **点发布后长期停在「正在发布」** 且控制台出现 `gateway_biz_verify_with_face` → 平台要求人脸二次验证，转 `browser_waiting_for_user_interaction` 请用户过人脸，不重复重试
