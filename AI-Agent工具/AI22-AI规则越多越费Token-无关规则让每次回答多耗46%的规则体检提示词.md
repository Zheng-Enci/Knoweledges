# AI 规则越多越费 Token：无关规则为什么让每次回答多烧 46% 的额度

> **核心结论**：规则不是写给你看的，是**每次提问都重新发给模型一遍**的。所以「不要、不许、禁止」这类只在出事时才生效的句子，会变成每一轮都在付费、却几乎不出力的常驻文本。一条被大量转发的实测是**同等任务下 token 消耗增加 46%**；本文再用一份真实在用的规则目录复算，7 个规则文件常驻约 **2.37 万 token**，是单条提问的 **150 倍以上**。解法不是删规则，而是分三层：常驻只留硬约束，特定任务搬进按需加载的 Skill，重复与冲突当场合并。

## 1. 一句话结论（Conclusion）

先把最容易误判的一点说清：**AI 不是「读了你的规则才回答」，而是「带着你的全部规则回答」** 🎭。

你写一句「不要用紫色」，它的成本和你写一句「按钮用蓝色」完全一样——都是每轮固定打包进上下文。区别在于：后者每轮都在指定怎么做，前者只在 AI 恰好想用紫色时才起作用。**规则写得越多，不代表越安全，只代表越贵。**

打个比方：出门带东西，**「钥匙、手机、钱包」是常驻**，因为每次都用得上；**「雨伞、创可贴、数据线」是按场景带**。而你现在的规则文件，更像把整个药箱背在身上出门——创可贴确实救过一次急，但它每一趟都在压你的肩膀 🎒。

## 2. 为什么规则会「每次都收费」（Mechanism）

大模型的对话是**无状态**的：服务端不记得你上一轮说过什么。你看到的「连续对话」，是客户端每轮把整段历史 + 系统提示 + 规则文件重新拼成一个请求发过去。

于是有三笔成本同时发生：

- **输入 token 成本**：规则文件有多少字，每轮就重发多少字。规则 2 万 token，问 10 轮就是 20 万 token 的输入。
- **注意力预算（Attention Budget）**：Anthropic 在 context engineering 指南里把上下文称为「有限的注意力预算」，并给出原则——找到**能达成目标的最小高信号 token 集**。无效规则挤占的不是钱，是模型真正该用来干活的注意力。
- **冲突解析成本**：A 条说「回答要详细」，B 条说「保持简洁」，模型必须先自行裁决再开工。裁决结果不可预测，这比浪费 token 更麻烦。

一条最反直觉的说法来自 Anthropic 的官方指南：为新一代模型**删掉 Claude Code 系统提示里 80% 以上的内容，评测上没有可测量的损失**。这个具体数值来自对指南的二次报道，不是本文实测，但它和「越少越高信号」的原则是一致的——被删掉的句子，长期只是在付费。

## 3. 46% 从哪来，以及怎么自己复算（Measurement）

**46% 来自一条在网上流传很广的测试**（同一任务、加入大量无关规则前后的 token 对比），本文没有复现它的具体环境，但给你一条能自己跑的复算路径——因为你真正需要的不是「信不信 46%」，而是「我的规则目录现在多重」。

复算只需两个量：**常驻字符数** 与 **单次任务本身的 token 数**。前者可以直接数，后者取你最近一次提问的平均长度即可。

本文拿一份真实项目在用的规则目录（`.trae/rules`，7 个 Markdown 文件）跑了一遍，结果如下。第 7 节的脚本指向你自己的规则目录（Cursor 的 `.cursor/rules`、Claude Code 的 `CLAUDE.md` 同理），也能跑出同一张表：

| 指标 | 实测值 | 说明 |
|---|---|---|
| 规则文件数 | 7 个 | 全部在每轮请求中常驻 |
| 总字符数 | 37,953 | 含表格、代码块、示例 |
| 总行数 | 1,233 | 平均每行约 31 字符 |
| 常驻 token 粗估 | 约 23,721 | 按 1.6 字符 ≈ 1 token 折算 |
| 否定式条目 | 81 条 / 3,806 字符 | 占全文字符 **10.0%** |
| 完全重复条目 | 13 组 / 521 字符 | 占全文字符 **1.4%**（下界；其中真正多出来的冗余 299 字符，0.8%） |

口径要交代清楚，否则数字会骗人 🔍：

1. **token 粗估**用「1.6 字符 ≈ 1 token」，这是中英混排的常见折算，**不是精确分词**；误差主要来自代码块与长英文词，实际值可能上下浮动 10%–20%。
2. **重复判定**口径为「去掉序号与标点后完全一致」，且只统计长度 > 8 字符的条目，所以 **1.4% 是重复率的下界**——语义相近但用词不同的重复不在其中，真实冗余只会更高。这 13 组按性质拆开看：**① 4 组**是 front-matter 与目录树的样式行（`alwaysApply`、`├── resources/` 这类），不是规则重复，属误报；**② 4 组**是 `system-prompt.md` 术语替换表内同一个词出现两遍（如「删除 → delete / remove」）；**③ 3 组**是 `system-prompt.md` 与 `文档写作铁律.md` 的验收清单条目重复；**④ 2 组**是同一文件内模板句与词表的重复。真正该合并的是 ②③④ 三类共 9 组。
3. **否定式条目**按关键词命中统计（禁止 / 不要 / 不许 / 不得 / 严禁 等），会误伤少数「禁止写成纯文本」这类有效约束，所以 **10.0% 是上界**，不代表 10% 全该删。

拿 23,721 除以一次普通提问的长度（按 150 token 估），**规则体积是任务本身的 150 倍以上**。这就是「你还没开始干活，预算已经花掉大半」的真实形态。

## 4. 三类最烧钱的规则（Root Cause）

### 4.1 为什么「不要什么」比「要什么」更贵

写规则时最容易忽略的一点：**否定式与正向式在账单上并不对称**。同样一条约束，「要什么」的写法贵在常驻，而「不要什么」的写法贵在常驻 **加上** 执行。

- **正向式给目标，否定式只划禁区。** 「输出 3 条要点、每条不超过 30 字」直接把目标摆出来，模型顺着生成就行；「不要写太多」只圈了一块不能进的地方，真正该写多少，得它自己补出来 🔍。
- **否定式要多做一遍自检。** 生成的过程中它拿不到方向，只能先写、再回头比对「有没有踩到禁止项」，踩到就重写。带思考链的模型更明显：它会额外花一段推理去判断「我这样算不算违反」，这笔钱直接记在输出与推理 token 上。
- **否定式常常缺省替代方案。** 「不要用 emoji」到底是用纯文本、换个符号、还是一句都别提？三种理解产出三种结果，于是同一句规则下你要反复纠偏，返工轮数又变成新的 token。

所以同一个约束，换个写法成本能差一个档：

| 否定式写法 | 正向式写法 | 模型需要做的 |
|---|---|---|
| 不要写太长 | 正文控制在 800–1200 字 | 直接对齐目标长度 |
| 不要用 emoji | 正文只用中文全角标点，不插图形符号 | 直接对齐字符集 |
| 不要问我确认 | 先给结论，再列 3 条依据 | 直接对齐结构 |

判断标准只有一句：**能写成「产出规格」的，就别写成禁令**。真必须禁的（危险操作、合规红线），后面补一句「改为 X」，把禁区翻译成目标——成本立刻从「先猜再自检」回到「照着做」。

想验证也不难，不用信本文：同一个任务跑两次，一次带否定式、一次带正向式，对比平台用量面板里的输出 token 与自己的返工次数。如果正向式那次明显更短、重写更少，说明原来那条禁令本来就是一条没写完的规格。

### 4.2 三类最贵的规则（Three Most Expensive）

不是所有规则都同样昂贵。按「每轮都付费、但触发率极低」这条线筛，最贵的是这三类：

**① 否定式堆叠。** 「不要用 emoji」「不要写总结」「不要问我确认」「不要用紫色」——每一条都只在极少数轮次生效，却 100% 常驻。十条否定式，等于十份保险，保费按天付，理赔一年一次。

**② 同一约束的多次复述。** 「保持简洁」在 system prompt 里写一遍，「回答不要冗长」在 rules 里写一遍，「控制篇幅」在某个 command 里再写一遍。模型读到第三遍不会更听话，只会更困惑：到底哪条优先？

**③ 特定任务的流程常驻。** 「发布文章时先登录内容平台后台，切到 Markdown 编辑器，粘贴正文，再逐个填封面、标签、摘要……」——这类步骤只在发布那一刻有用，却天天占着上下文。**它是流程，不是约束，天生该按需加载。**

三条合起来解释了一个现象：**规则文件越大，模型越容易「选择性失聪」**。不是它不听话，是信号被自己人埋了。

## 5. 一条可直接发给 AI 的规则体检提示词（Copy-Ready Prompt）

下面这段可以原样发给任何支持读取项目配置的 AI 智能体（Trae、Cursor、Claude Code 等）：

```markdown
请帮我检查目前给你设置的所有规则和工作要求，找出重复、冗余、冲突和不常用的内容。

要求：
1. 先列清单：逐条列出当前生效的规则来源（rules / commands / skill / 全局配置），
   标注每条大致占用多少字符。
2. 再分类：把每条规则归入「常驻硬约束」「按需流程」「重复或冲突」「可以删除」四类。
3. 输出冲突项时必须成对给出：A 条 vs B 条，冲突点是什么，建议保留哪条。
4. 把特定任务的流程整理成可按需调用的 Skill，给出落地位置与目录结构。
5. 不要删除影响安全和工作质量的规则，删除项一律先列出来等我确认。
6. 最后输出优化方案：改哪几个文件、每处删多少字、预计省下多少 token。

先只输出方案，不要直接改文件，等我确认后再动手。
```

这段提示词之所以有效，靠的是三个可判定动作：**列清单**（能数）、**分四类**（能归档）、**先方案后执行**（能止损）。写成「帮我优化一下规则」，AI 只会给你一段漂亮但无从验收的总结 🙃。

## 6. 体检报告怎么读：四类输出与处理动作（Reading Report）

拿到报告别急着全删。四类输出对应四种动作，判断标准只有一条：**这条规则多久会真正生效一次？**

| 报告分类 | 判断特征 | 处理动作 |
|---|---|---|
| 常驻硬约束 | 每一轮都可能违规，如「提交信息用英文」 | 保留，可压缩措辞 |
| 按需流程 | 只在特定任务触发，如平台发布步骤 | 移入 Skill 或 command |
| 重复或冲突 | 同一意思出现两次以上，或两条互相矛盾 | 合并为一句话，冲突项择一 |
| 可删除 | 从没生效过，或已被模型默认行为覆盖 | 删前留一周观察期 |

一个容易踩的坑：**别把「安全类规则」和「风格类规则」混在一档处理**。安全、权限、不可逆操作的确认，永远是常驻；而「语气亲切」「多用比喻」这种，完全可以让位给按需加载。

## 7. 完整可运行脚本：一条命令数清规则体积（Runnable Audit）

下面这个脚本复制保存成 `rule_audit.py`，在项目根目录执行 `python rule_audit.py .trae/rules` 即可。第 3 节那张表的全部数字都由它算出，你可以换任意目录复跑。

```python
"""规则体检脚本：统计规则目录的体积、重复条目与否定式条目占比。

使用示例:
    python rule_audit.py .trae/rules

参数:
    命令行第 1 个参数为待体检目录，缺省为 .trae/rules
返回:
    无返回值，结果直接打印到标准输出
"""
import os
import re
import sys
from collections import Counter

# 判定「否定式规则」的关键词：这类句子只在违规时生效，却全程占用常驻 token
NEGATIVE_WORDS = ("禁止", "不要", "不许", "不得", "不准", "不能", "勿", "严禁")

def normalize(line):
    """归一化一行规则用于查重：去掉列表符号、序号、标点与强调符。

    参数:
        line: str，原始规则行文本
    返回:
        str，归一化后的文本，可直接用于相等比较查重
    """
    text = re.sub(r"^[\s\-\*\d\.\)、]+", "", line)                 # 去掉列表符号与序号
    text = re.sub(r"[，。；：、（）()\[\]【】\"'`*#]", "", text)     # 去掉标点与强调符
    return text.strip()                                            # 两端空白一并去掉

def main():
    """遍历目录下所有 .md 规则，输出体积、重复条目与否定式占比。

    参数:
        无（目录从 sys.argv[1] 取，缺省为 .trae/rules）
    返回:
        None，统计结果直接打印到标准输出
    """
    root = sys.argv[1] if len(sys.argv) > 1 else ".trae/rules"      # 默认体检 .trae/rules
    files, items, total = [], [], 0                                 # 汇总容器
    for name in sorted(os.listdir(root)):                           # 固定顺序，保证结果可复现
        if not name.endswith(".md"):                                # 只统计 markdown 规则
            continue
        text = open(os.path.join(root, name), encoding="utf-8").read()
        lines = [l.strip() for l in text.splitlines() if l.strip()]  # 丢弃空行
        total += len(text)                                          # 累计字符数
        files.append((name, len(text), len(lines)))                 # 逐文件体积
        items += [(name, l) for l in lines]                         # 逐条规则入池

    normed = Counter(normalize(l) for _, l in items if len(normalize(l)) > 8)
    dups = {k: v for k, v in normed.items() if v > 1}               # 归一化后完全一致才计重复
    dup_chars = sum(len(k) * v for k, v in dups.items())            # 重复占用字符（近似）
    neg = [l for _, l in items if any(w in l for w in NEGATIVE_WORDS)]
    neg_chars = sum(len(l) for l in neg)                            # 否定式占用字符

    print(f"目录: {root}")
    for name, chars, n in files:
        print(f"{name:34s}{chars:8d}{n:6d}")                        # 逐文件明细
    print(f"{'合计':34s}{total:8d}{len(items):6d}")
    print(f"\n重复组数 {len(dups)} / 占用 {dup_chars} 字符 ({dup_chars/total:.1%})")
    print(f"否定式 {len(neg)} 条 / 占用 {neg_chars} 字符 ({neg_chars/total:.1%})")
    print(f"常驻 token 粗估: 约 {round(total/1.6)}（1.6 字符 ≈ 1 token）")

if __name__ == "__main__":
    main()
```

脚本故意只做「可数的事」：体积、完全重复、否定式命中。语义重复和规则冲突它判不了——那部分交给第 5 节的提示词，让模型读内容判断。**机器数体积，模型判语义，两边各干自己擅长的活。**

## 8. rules / commands / skill 该怎么分工（Placement）

体检报告出来后，规则该往哪放？按「触发频率」分三层，边界很清楚：

- **rules（常驻）**：每轮都该生效的硬约束。提交信息语言、危险操作确认、代码注释语言——这类宁可留，也不要为了省 token 删掉。
- **commands / skill（按需）**：只在特定任务调用的流程。平台发布步骤、文档生成规范、某类代码的目录结构——用到才加载，不用时不占位。
- **memory（沉淀）**：项目历史决策与踩坑。它不是规则，不该挤在 rules 里冒充约束。

这个分工在[Agent 规则管理：让 Memory 做索引、让 Skill 存规则](https://juejin.cn/post/7703445535818317833)里用实测讲过：**Skill 的机制正是「启动时只加载几十个 token 的元数据，命中后才加载正文」**。微软的 Agent Skills 文档把这个数字写得更具体：每个 Skill 的元数据广告约 100 token，命中后加载的正文建议控制在 5000 token 以内。

换句话说：把一条 800 字的发布流程从 rules 搬进 Skill，你省下的不是 800 字，而是**每轮 800 字**。

## 9. 对照表：症状 → 原因 → 解法（Troubleshooting）

| 症状 | 原因 | 解法 |
|---|---|---|
| 同样的问题，这周比上周贵 | 规则文件只增不删，每轮重发 | 跑规则体检脚本，先看总体积 |
| AI 明明有规则却总违反某一条 | 信号被大量低价值条目稀释 | 把该条提到 rules 首段，其余下沉 |
| 两条规则互相矛盾，输出时好时坏 | 同一约束写了多处且措辞不同 | 合并为一句话，只留一处 |
| 换了新模型后表现变差 | 旧规则在过度约束新模型 | 删掉已被默认行为覆盖的条目 |
| 发布流程每次都要重复解释 | 流程常驻在 rules 里，而非 Skill | 抽成 Skill，按需加载 |

三个补充判断：

**① 规则不是越多越安全。** 一条永不触发的规则，安全收益为零，成本 100%。

**② 精简 ≠ 删干净。** 安全类、不可逆操作类规则必须常驻；精简的是「描述性」「鼓励性」「重复性」三类。

**③ 改完要观察。** 一次删太多会踩到隐形依赖。建议每轮只动一个文件，观察 3–5 次任务再继续。

## 10. 发布前验收清单（Checklist）

- [ ] 跑过一次体检脚本，记录了优化前的字符数与 token 粗估
- [ ] 重复条目已合并，冲突条目已择一并写明保留理由
- [ ] 特定任务流程已下沉到 Skill 或 command，rules 里只留硬约束
- [ ] 安全类、不可逆操作类规则仍在常驻层，一条没少
- [ ] 改完后重跑脚本，体积下降且规则条数减少
- [ ] 连续 3 次真实任务未出现「该守的规则没守住」

**AI 不是规则越多越聪明，是规则越精准、调用越合理才越高效**：规则超过两屏，或开始反复补同一条约束时，就该体检；还不到十条，先写完再说。

本专栏《AI Agent 工具》聚焦提示词工程、上下文管理与规则治理，每篇都配一段可直接运行的脚本或提示词，每周更新一篇。想按顺序读完，可在专栏页订阅。
