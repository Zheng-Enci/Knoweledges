## P01 · 封面

> 卡片职责：抛钩子 + 定锚主题，标题 + 核心数字

- 规则到底该写进 **Memory** 还是 Skill？
- 让 Memory 做索引，让 Skill 存规则
- **200 行** 常驻上限，写多了 AI 看不到

## P02 · Memory 有硬上限

> 卡片职责：摆出官方约束数字，建立「有上限」的认知

- 别争论，官方建议 CLAUDE.md 文件控制在 **200 行**以内
- 在 200K 上下文里，它每次要占掉约 **40000 字符**
- 自动记忆的 MEMORY.md 只读前 **200 行 / 25KB**，哪个先到用哪个
- 结果：写得太长，靠后的规则这轮根本加载不进来 😅

## P03 · 全塞 Memory 两代价

> 卡片职责：讲清两种付代价，制造痛点

- 代价一：规则排在 **200 行 / 25KB** 之外，会话里根本没加载
- 你以为写了「先审代码再提交」，AI 这轮却看不到
- 代价二：几十条不同主题规则每轮都被**从头读一遍**
- 无关规则抢 attention，该执行的反而被稀释 😮💨

## P04 · 像常驻内存会爆掉

> 卡片职责：用生活化类比把抽象代价讲透

- Memory 像电脑的**常驻内存**，开机就占着
- Skill 像**按需加载**的软件，你点开才载入
- 把所有软件都做成开机自启，内存会爆、还互相抢资源
- 这就是规则全塞 Memory 的后果：又挤又乱 😵

## P05 · Memory 只做索引

> 卡片职责：点出核心解法，一锤定音

- **Memory** 只记「该读哪个 Skill」，是张索引卡片
- 具体规则、SOP、手册**全部写进 Skill**，别塞 Memory
- 目标 signal-dense：每行都值回它占的上下文
- 口诀：每轮都知 → Memory；特定任务/多步流程 → Skill

## P06 · Skill 加载为啥挤不掉

> 卡片职责：讲清 Skill 三级加载，解答「想不起来读」的疑虑

- 启动只加载元数据，约 **100 token**
- 完整 SKILL.md 正文（<**5k token**）只在被触发时才进上下文
- 正文平时不占空间，所以不存在「写太多被截断」
- 触发后临时读进全部规则，用完即释放 ✨

## P07 · 一条规则该放哪

> 卡片职责：给可落地的判断口诀，拿去就能用

- 多步流程 / 操作手册 → 一定进 **Skill**
- 每轮都必须知道 → 进 **Memory**，当常驻索引
- 只在某个任务才需要 → 进 Skill，用 description 自动触发
- 拿不准 → 默认进 Skill，**最不容易出错** 👍

## P08 · 一条判据就够

> 卡片职责：末页给判据式结论 + 一句互动钩子

- 判断标准就一条：这条规则 **AI 每轮都要看**吗
- 是 → 进 Memory；否 → 进 Skill，**别全塞 Memory**
- 别让 Memory 超 **200 行 / 25KB**，超了遵守度就降
- 你现在的规则是全部挤在 Memory，还是老早分了 Skill？A 全挤在 Memory B 早分了 Skill
