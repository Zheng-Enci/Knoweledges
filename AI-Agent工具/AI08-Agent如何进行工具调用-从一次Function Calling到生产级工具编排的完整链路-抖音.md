- 副标题：它只负责「想」，你才负责「做」
- 核心数字：**一次闭环** = 请求 + 决策 + 执行 + 回传

## P02 · 模型只会「写指令」

> 卡片职责：破除误解，讲清模型不是执行者

- Agent 调用工具，不是模型自己跑去调函数
- 模型只是推理引擎，**没权限**真去访问数据库或 API
- 它唯一干的：输出一个**结构化调用指令**
- 用哪个工具、参数填什么，全是它「写」出来的
- 真正执行的，是**你的应用程序** 🎭

## P03 · 四阶段闭环

> 卡片职责：给出完整链路的骨架

- **请求**：把用户提问 + 工具清单一起发给模型
- **决策**：模型判定要不要调用，输出工具名 + 参数
- **执行**：应用按工具名找到函数，真实跑一遍
- **回传**：把结果以 tool 角色喂回给模型
- **再生成**：模型基于结果，产出最终自然语言回答

## P04 · description 决定成败

> 卡片职责：讲清工具描述是最被低估的一环

- 模型决定「何时调用、参数怎么填」，唯一依据是 description
- 描述写得含糊，模型就**瞎猜**，要么不调用要么传错
- 黄金法则：用动词开头，写清**何时用、何时不用**
- 量表：**description** 是影响准确率的**最大单一因素**
- 花在打磨描述上的功夫，回报远高于调 prompt

## P05 · 工具名要语义化

> 卡片职责：讲清好名字让模型一眼读懂

- `search_docs` **胜于** `docs`
- 模型能从名字里读懂意图，选对工具
- 参数要在 schema 里写清类型、必填、单位、枚举值
- Vague schema 会诱导模型**编造参数**或者选错工具
- 好名字 + 准描述 = 调用更稳定

## P06 · 模型会「骗」你

> 卡片职责：提醒参数必须校验，不能直接执行

- 拿到模型的 `arguments`，**千万别直接执行**
- 它是基于文本的**猜测**，不是可靠数据
- 会把字符串列表输出成 `"P001,P002"` 这种类型错误
- 会编造你根本不存在的城市名、漏掉必填参数
- 所以执行前，必须过一层**参数校验**

## P07 · 高危操作要二次确认

> 卡片职责：把「执行前防线」这一步讲透

- 校验结构、类型、必填项，用 JSON Schema
- 涉及删除、发送、转账，再加**二次确认**
- 用户身份、租户范围，也要校验权限
- 原则：模型输出永远是**候选参数**
- 经过校验与清洗，才变成**可执行参数** 🔒

## P09 · 什么时候别用工具

> 卡片职责：讲清边界，避免过度设计

- 工具调用有延迟、有成本、有出错风险
- 纯知识问答、语义理解、文本生成，**直接回答**即可
- 判断一问：模型不查外部数据，能答对吗？
- 能答对就别上工具，又稳又快又省
- 把工具留给**模型自己答不了**的场景

## P10 · 一句话总结

> 卡片职责：末页判据 + 互动钩子

- 模型当**决策者**，应用当**执行者** 🎯
- 你要做的是：把工具描述打磨准，把参数校验做扎实
- 判断：需要实时数据或真实动作 → **用工具**；模型能答对 → **不用**
