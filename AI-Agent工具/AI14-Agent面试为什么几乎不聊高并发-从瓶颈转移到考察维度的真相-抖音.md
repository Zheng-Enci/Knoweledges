## P01 · 封面

> 卡片职责：抛钩子 + 定锚主题，点破「Agent 面试高并发」核心名词

- **Agent 面试为什么不聊高并发？**
- 副标题：不是不重要，是瓶颈根本不在并发
- 核心数字：最强 Agent 日常任务完成率仅 **33.3%**，先解决对不对

## P02 · 先看 Agent 面试到底在考什么

> 卡片职责：列出真实考察版图，铺垫「为什么没并发」

- 一场典型 Agent 面试，考这几块：Agent 认知与架构、规划推理、工具调用、记忆管理、评测兜底。
- 几乎每场开口都问：Agent 和普通 LLM 应用、工作流的区别是什么。
- 每一块问的都是「Agent 特有的能力」，没有一块在问「QPS 打到多少」。
- 这不是巧合，它反映的是岗位的**真实痛点**在别处 🎯。

## P03 · 原因一：瓶颈不在并发，在正确率

> 卡片职责：讲核心原因，给出完成率数据

- 传统后端核心矛盾是并发：用户一多数据库扛不住，所以要聊高并发、缓存、限流。
- Agent 核心矛盾是**正确率**：连一次任务都经常做不对，并发再高也只是「同时失败一万次」。
- ClawBench 实测最强 Agent 日常任务完成率也就 **33.3%**，这是它现在的阶段。
- 类比 🎭：一道题都算不对的计算器，你会关心它一秒算几次吗？只会在意对不对 ⚡。

## P04 · 先 0 到 1，再 1 到 N

> 卡片职责：讲优先级逻辑，解释「不是不重要是没排上」

- 高并发解决的是「1 到 N」的放大问题；Agent 要解决的是「0 到 1」做没做对。
- 所以面试官问的是「工具异常怎么处理」「怎么做评测」，而不是「怎么抗百万 QPS」。
- 这不是说高并发没用，而是**没到谈它的时候**——房子没盖好先别研究物业费。
- 一句话：**先让一个任务做对，再谈让一万个同时跑** 🏗️。

## P05 · 原因二：高并发是通用能力，不构成区分度

> 卡片职责：讲考察维度差异，给对比

- 高并发是「通用后端能力」，面 Java/Go 后端时早被考过了，到这里没有信息增量。
- Agent 岗要区分的是：你懂不懂 **Agent 的独特工程问题**。
- 独特问题包括：上下文管理、工具编排、记忆一致性、幻觉兜底、多 Agent 协调、评测。
- 所以考察从「扛住流量」转成了「让任务可靠完成」 🔍。

## P06 · 原因三：高并发「换了名字」出现

> 卡片职责：打破「完全不考」的误解，给映射表

- 高并发没消失，只是换了名字藏进 Agent 系统设计里。
- 数据一致性 → Agent **状态持久化**，高并发下不写乱。
- 任务调度 → 任务拆解形成的 **DAG** 编排与执行。
- 超时/重试/熔断 → 工具调用保护；并发锁 → 多 Agent 共享资源互斥 ⚠️。

## P07 · 反方观点：Agent 本质是分布式系统

> 卡片职责：引入正反辩证，体现思考深度

- 有面试官提出：复杂 Agent 系统本质就是**分布式异步执行系统**。
- 所以状态要存（考 Redis 思维）、DAG 要执行（考拓扑排序）——高并发以系统设计形式考。
- 这个观点对一半：它考的是**并发正确性思维**，不是「高并发调优细节」。
- 结论：高并发从「性能题」降级成了「正确性题」——不问怎么扛，问怎么不出错 ⚖️。

## P08 · 面试官真正想听：规划-执行-验证闭环

> 卡片职责：给加分叙述结构

- 规划：只输出结构化计划，先想清楚要几步，别边想边做。
- 执行：每个工具都有 Schema、权限、超时——可控、可管、可停。
- 验证：规则 + LLM Judge 双层检查；**高危动作必须人工确认**。
- 加分点：讲清「为什么部分流程用工作流不用 Agent」「bad case 怎么回放」✅。

## P09 · 该准备什么：能力优先级清单

> 卡片职责：把分析收敛成可执行清单

- P0 必须张口就来：**Agent 认知与架构、规划-执行-验证闭环、工具调用可靠性**。
- P1 加分项：记忆管理、评测与兜底。
- P2「懂就行」：并发正确性思维（状态不写乱、DAG、互斥）。
- P3 放低：高并发调优细节，了解即可，不是 Agent 岗第一考察点 📌。

## P10 · 判断收尾 + 互动钩子

> 卡片职责：给判据式结论 + 唯一一句互动钩子

- 判断标准：**岗位瓶颈是「任务做不对」还是「扛不住流量」**——前者准备 Agent 可靠性。
- 面 Agent 应用工程：重点练认知、闭环、工具、评测，比背 QPS 回报高。
- 面大模型平台/推理服务：那才真考并发与容量规划。
- 一句话收束：**高并发没被抛弃，只是在这个岗位里从性能题变成了正确性题**。
