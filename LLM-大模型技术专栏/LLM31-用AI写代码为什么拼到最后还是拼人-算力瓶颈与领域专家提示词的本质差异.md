# 用 AI 写代码为什么拼到最后还是拼人：算力瓶颈与领域专家提示词的本质差异

2026 年，大模型的能力还在持续提升，但有一件事始终没变——**算力永远追不上需求**。更关键的是，用 AI 写代码这件事，能不能用好、能不能写对，**根本不取决于模型有多强，而取决于你有多懂**。很多人以为用了 AI 写代码就能「躺赢」，结果却撞上最坏的情况：**遇到 bug 不知道怎么修，连问题出在哪都看不出来**。

本文不说空话，直接回答三件事：**为什么算力追不上（现状）、领域专家凭什么一眼看出问题（专业能力）、怎么把专家经验变成 AI 听得懂的提示词（方法论）**，并给出一段可以跑的对照代码。

## 1. 拼到最后拼的是人：一个反常识的结论（The Human Factor）

先说结论：**AI 写代码，拼到最后拼的还是人。** 不是模型，不是算力，是人的专业能力。

这一年下来，大模型的能力一直在提升，但有一点始终没变——**「算力永远跟不上」**。你会发现一个很扎心的现实：当模型能力上去了，卡的是硬件；当硬件勉强跟上了，卡的又是人的使用水平。AI 工具再强，它也只是放大镜，**你本身有多专业，它放大的就是多大的专业；你不专业，它放大的就是你的盲区**。

> 最典型的就是「vibe coding（氛围编程）」带来的幻觉。现在很多人用它几分钟就能「写」出一个 App，看起来很爽，但这种爽是有代价的。安全研究机构对 5600 多个 vibe coding 应用扫描后发现：超过 2000 个安全漏洞、400 多个暴露的密钥、175 例个人隐私数据泄露。**能跑，不代表能上线；能用，不代表懂。** 这就是「拼的是人」这句话最直接的注脚。

为什么是这个结论？因为 AI 写代码的本质，是**你问什么、它给什么**。你问不出高质量的问题（提示词），它就给你平庸的答案；你分不清它给的答案对不对，你就只能照单全收，然后被埋在它埋下的坑里。**低垂的果实（low-hanging fruit）被摘完之后，剩下的每一寸进步都靠人。**

这个主题，其实能在本专栏前序文章里找到呼应。在[agent 为什么需要自进化](https://doi.org/10.48550/arXiv.2511.06449)那篇里我们讲过，agent 光靠参数堆砌会「训练完就静止」，必须靠经验机制才能持续变强——而经验恰恰来自懂行的人如何设置反思、如何沉淀策略。**模型的瓶颈要靠机制补，机制的瓶颈要靠人来设计。**

## 2. 算力永远跟不上：瓶颈的底层逻辑（Compute Bottleneck）

为什么说「算力永远跟不上」？这不是悲观，而是结构性事实。

**需求端在指数级膨胀。** 中国信通院数据显示，截至 2026 年 6 月，我国日均 Token 调用量已突破 500 万亿，相比 2025 年末的 100 万亿大幅提升。模型能力越强、智能体（agent）越普及，调用量就越大，对算力的渴求就越无限。

**供给端被多重瓶颈卡死。** 国家发展改革委宏观经济研究院研究员张林山指出，生成式 AI 应用的井喷催生海量算力需求，科技巨头与初创企业纷纷投身「百模大战」，导致对高性能 GPU 的需求暴涨；而供给端受产能、先进制程、高端卡进口限制等多重约束，缺口持续扩大。「算力价格上涨，根本原因是供需失衡」，赛智产业研究院智能经济研究所所长李铭岩说得直白。

**架构本身也在成为瓶颈。** 中国信通院《AI 计算节点发展研究报告（2026 年）》指出，为应对千亿、万亿参数大模型训练对通信性能的极致要求，传统以服务器为单元、依赖外部网络堆叠的算力架构，已成为制约算力效能释放的主要瓶颈。当前 AI 计算节点的演进主线正在从「以连接 CPU 为中心」转向「以 GPU 互联为中心」，靠架构重构来挤效率。

> 把这层逻辑翻译成人话：**算力就像路上的车，需求是车流，供给是车道。车流年年翻倍，车道却在被各种路障（产能、制程、限购）卡着。** 所以别指望哪天算力突然管够，那既不现实，也不是解决问题的关键。真正能撬动效率的杠杆，不在硬件上，而在「你怎么用」。

## 3. 最坏的情况：不懂技术的人用 AI 写代码（The Worst Case）

如果说算力瓶颈是「硬约束」，那「不懂技术还硬写」就是最容易被忽略的**软灾难**。用 AI 写代码最坏的情况是什么？**是你根本就不懂这个技术，告诉 AI 不知道怎么写，它写完你也看不懂。** 一旦它埋了个 bug，你能做的事只有干瞪眼——**修它一整个下午，你都不知道从哪下手。**

这就是「vibe coding」最残酷的一面。它让「写代码」的门槛降到了前所未有的低，但**调试（debugging）的门槛一点都没降**。你可以让 AI 五分钟「写」出一个 app，但当它跑出奇怪的行为时，你没有能力判断「这是幻觉依赖、是状态没重置、还是逻辑根本错位」。

> 前面第 1 章提的安全数据已经说明问题：5600 多个 vibe coding 应用，扫出 2000+ 个漏洞、400+ 个暴露密钥。这些应用的创建者大多不具备安全知识。**他们不是故意埋雷，是根本看不见雷。**

不懂行的人踩的坑，往往集中在几类：

**一是「幻觉依赖（hallucinated dependencies / slopsquatting）」。** AI 会编出看起来很像真的包名和方法名。懂行的人第一反应是「去 lockfile 里核对这个 import 到底存不存在」；不懂行的人直接 `pip install`，于是装上了攻击者抢注的同名恶意包。

**二是「做对了结构，做错了意图」。** 一个很典型的例子：AI 写的 `try...catch` 块里，catch 里只 `console.log(error)`，然后什么都不做——没有 fallback、没有提示用户、没有重试。**代码不崩溃，只是「安静地坏掉」**。外行看起来一切正常，只有懂意图的人知道这功能已经废了。

**三是「反向追因」无从谈起。** 真正的 debug 高手，是从症状倒着往回找（trace backwards from the symptom）：「第二次上传绕过了弹窗」→ 从上传执行点开始问「是什么条件让它跑了」→ 找到那个没被重置的标志位。**这套逆向推理的前提，是你脑子里有一个「正确的系统长什么样」的模型。** 你没有这个模型，AI 再聪明也救不了你。

> 把这三类坑连起来看，会得出一个很扎心的结论：**AI 降低了「写出代码」的门槛，却丝毫没有降低「读懂代码、排错代码」的门槛。** 于是那些只享受了前半段红利的人，会结结实实地摔在后半段上。**门槛并没有消失，它只是从「写」转移到了「判断」上。**

## 4. 领域专家凭什么一眼看出问题（Expert's Eye）

前面讲的是「不懂的人有多惨」，这一章讲另一面——**懂的人凭什么能一眼看出问题**。这恰恰是「拼到最后拼的是人」这句话的核心论据。

有个很生动的真实案例：**年轻工程师**用 AI 写代码，遇到 bug 的第一反应是「把报错信息丢给 AI 分析」；而一个只会「古法编程」的**老工程师**，第一反应却是 **「先猜机器哪里不舒服」**。他知道一个看似随机的崩溃，可能是因为某个寄存器的某个位没置位；一次通讯失败，可能是线缆过长导致信号衰减；一个数据错乱，可能是中断嵌套太深导致栈溢出。**他脑子里装着一整套「机器在想什么」的模型**，所以他能从蛛丝马迹里反推出真正的病因——而这是 AI 和报错文本都给不了你的。

为什么 AI 工具做不到这一点？**因为 AI 擅长的是「模式识别（pattern recognition）」，而不是「意图理解（intent-level understanding）」。** 各类 AI code review 工具的实测都指向同一个结论：它们能稳定抓出**符合已知模式**的错误（未用变量、不可达代码、潜在空指针、语言特定的反模式），但抓不住**没有模式可循**的错误——业务逻辑错位、AI 幻觉出的认证流程、跨服务越权、高并发下的竞态条件（race condition）。

> 换句话说，**AI 是「扫描仪」，只能看到表面；专家是「医生」，能根据症状推断体内发生了什么。** 扫描仪扫不到的那种病，才真正要命。这也是为什么几乎所有关于 AI 代码审查的建议都会补一句：**自动工具无法检测意图级错误，对 AI 生成的代码，专家人工审查不可替代（non-negotiable）。**

而资深工程师在 AI 时代并没有被淘汰，只是转岗了。AI 接管了**机械性的检查**（风格违反、空指针、文档缺失）之后，资深开发者把精力转移到更高价值的事上：**架构审查**（这符不符合我们的系统设计）、**安全分析**（这个领域特有的威胁是什么）、**性能评估**（它能扛住规模吗）、**以及带教**（告诉新人为什么 AI 的这条建议很重要）。这四件事，恰恰是 AI 目前最不擅长的。

专家能力的来源，可以拆成三个层面：

1. **领域模型（mental model）**：脑子里有「系统理应如何运转」的完整图景，所以能判断「正常」与「异常」的边界。
2. **经验指纹（pattern of failure）**：踩过足够多的坑，知道「这类问题通常长什么样、藏在哪里」。
3. **归因能力（root-causing）**：能从表象逆推根因，而不是被表象牵着走。这三层，靠的都是**人**的长期积累，不是模型参数能替代的。

## 5. 专业提示词：把专家经验注入 AI（Professional Prompts）

前面说了「专家有一双慧眼」，那怎么把这双慧眼「借给」AI？答案是——**把专家的经验、约束、验收标准，写进提示词（prompt）里**。提示词就是你递给 AI 的任务说明书，说明书写得多专业，AI 的产出就有多专业。

先看一个扎心的量化事实。有数据显示，**84% 的开发者已经在用 AI 工具，但只有不到 30% 的人能稳定获得可用于生产的代码**。原因不是模型不好，而是**模糊的提示词只能产出平庸的代码**——大多数开发者把 AI 当 Google 用，直接丢一句「write a function to sort an array」，然后抱怨结果像 2010 年的 StackOverflow 答案。

还有一个更直观的对比：**模糊描述生成的代码可能需要 80% 的返工，而结构化提示词能把一次通过率提升到 80% 以上**。同一个模型、同一个需求，**提示词写得清不清晰，能差出好几倍的效率**——这不是玄学，是「把话讲清楚」的工程学。

那「专业提示词」到底长什么样？它并不是什么神秘咒语，而是包含六个要素的结构化任务说明书：

| 要素 | 作用 | 反例（模糊） | 正例（专业） |
|---|---|---|---|
| 角色（Role） | 让模型以特定身份/视角作答 | 「写个排序函数」 | 「你是一名资深 Python 后端工程师」 |
| 上下文（Context） | 交代模型无法推断的背景 | 不交代 | 「这是处理百万级订单的 REST API」 |
| 任务（Task） | 一个明确的可交付物 | 「优化一下」 | 「把接口响应耗时降到 P95 < 200ms」 |
| 约束（Constraints） | 限定范围、禁止项 | 不限定 | 「Python 3.12，不引入新依赖，不改函数签名」 |
| 输出格式（Format） | 规定返回结构 | 随意 | 「返回 JSON，字段为 `code`/`message`/`data`」 |
| 验收标准（Criteria） | 明确怎样算「做对了」 | 缺失 | 「pytest 全绿 + 耗时降低 30%」 |

> 这份表格的本质，是把**专家脑子里那些「不言自明」的隐性知识，翻译成 AI 能听懂的统一语言**。专家写提示词快，不是因为他手速快，而是因为他**知道该取舍什么、该禁止什么、该用哪个方案、什么才算「对」**。这些判断，恰恰是新手最缺、也最值钱的部分。

把专家经验注入提示词，可以归纳成三个可复用的动作：

1. **给具体目标，别给指令**。不要只说「优化一下」，要说「把接口响应耗时降到 P95 < 200ms」。可衡量的验收标准能逼 AI 产出可判断的结果。
2. **给约束，尤其给「不要什么」**。明确「不引入新依赖」「不改签名」「不删字段」，能阻止 AI 越界发挥，也防止它膨胀出你不想要的东西。
3. **给环境与示例**。告诉它「Linux + 有复现日志」，或者给一个 few-shot 例子，让 AI 对齐你的业务语境，而不是套用通用模板。

> 一句话总结这一章：**提示词不是玄学，是「把话说清楚」的工程。** 你能把需求讲多清楚，AI 就能把活干多好——而「讲清楚」这件事，靠的是专业知识，不是打字速度。

## 6. 症状 → 原因 → 解法对照表（Symptom-Cause-Solution）

前面五章拆开了「算力瓶颈」「不懂的坑」「专家的慧眼」「提示词的方法」，这一章把「你会在 AI 写代码时撞到的坑」和「怎么治」捋成一张可以对照的表。如果你正在用 AI 写代码，照着症状对号入座即可。

| 症状 | 原因 | 解法 |
|---|---|---|
| 用 AI 写完代码，遇到 bug 修一下午都不知道从哪下手 | 不懂这个技术，没有「正确系统」的心理模型 | 先补领域知识，别急着让 AI 写；请专家 review 或自己先读通代码 |
| AI 生成的代码能跑，但一上线就出安全问题（密钥泄露、漏洞） | 不具备安全知识，看不出 AI 埋的雷 | 关键领域审查 + 用工具扫描，禁止直接带上生产 |
| AI 给出看起来很像真的包名/方法名，装完发现是恶意包 | 幻觉依赖（slopsquatting），未核对 lockfile | 核对每个 import 是否存在、版本是否匹配，不盲信 AI 建议 |
| 逻辑「很对」但不是业务要的，静悄悄地坏掉 | AI 做对了结构、做错了意图（如 catch 里只 log 不处理） | 明确验收标准，让专家判断「是否符合业务意图」 |
| 提示词越简单，代码越通用、越不像你的项目 | 缺上下文、缺约束，模型只能套通用模板 | 用角色+上下文+约束+输出格式+验收标准写结构化提示词 |
| 算力不够用，模型响应慢、卡顿 | 供需失衡+架构瓶颈，短时间无解 | 别指望硬件，转向优化「怎么用」（提示词、缓存、路由） |
| 觉得 AI 很强，自己随便用就能「躺赢」 | 误解了「写代码门槛」与「判断门槛」的区别 | 把重心放在提升专业能力与判断力，而非堆工具 |

> 这张表想传达的判据是：**绝大多数「AI 写代码翻车」的坑，根子都在「人的判断力不足」，而不是「模型不够强」或「算力不够」**。所以解法优先级永远是「先提升人，再优化工具」。

## 7. 一段可运行的对照代码：新手 prompt vs 专家 prompt（Runnable Code）

前面全是理论，这一章给一段可以直接跑的代码，演示「**新手 prompt**」和「**专家 prompt**」让同一个 AI 输出同一段功能时的差别。它用一个极简的 `CodeGenerator` 模拟「提示词 → 生成代码 → 质检（返工判断）」的流程。

```python
# -*- coding: utf-8 -*-
"""
AI 写代码「新手 prompt vs 专家 prompt」的最小对照 demo：
同一个模型、同一个需求，只差提示词质量，产出与一次通过率天差地别。
本 demo 只用标准库，无需额外安装依赖。
"""


def generate_code(prompt):
    """按提示词质量模拟 AI 生成的代码（这里用提示词质量打分近似返工率）。"""
    # 模拟：模糊提示词 → 生成代码需要大量返工；结构化提示词 → 一次通过
    if "验收标准" in prompt and "约束" in prompt and "输出格式" in prompt:
        return "一次性通过，代码可直接上生产", 0.0    # 返工率 0%
    return "代码能跑但需返工，存在安全隐患", 0.8        # 返工率 80%


def novice_prompt():
    """新手 prompt：模糊指令，缺上下文与约束。"""
    return "帮我写一个排序函数"


def expert_prompt():
    """专家 prompt：结构化任务说明书，含六要素。"""
    return (
        "你是一名资深 Python 后端工程师。"
        "任务：为百万级订单的 REST API 实现一个稳定的排序函数。"
        "约束：Python 3.12，不引入新依赖，不改函数签名。"
        "输出格式：返回 JSON，字段为 code/message/data。"
        "验收标准：pytest 全绿 + 接口耗时降低 30%。"
    )


if __name__ == "__main__":
    # 模拟同一个模型分别接收两类提示词
    print("===== 新手 prompt =====")
    novice_result, novice_rework = generate_code(novice_prompt())
    print(f"AI 产出: {novice_result}，返工率: {novice_rework * 100:.0f}%")

    print("\n===== 专家 prompt =====")
    expert_result, expert_rework = generate_code(expert_prompt())
    print(f"AI 产出: {expert_result}，返工率: {expert_rework * 100:.0f}%")

    print("\n结论：同一个模型，提示词写得清不清晰，返工率可从 80% 降到 0%。")
```

**代码想说明什么？** 核心是 `generate_code` 里的那一行判断——**「验收标准」「约束」「输出格式」三个词在不在提示词里，直接决定了结果是一次通过还是 80% 返工**。生产环境里，你会把这个函数换成真实的模型调用 + 测试套件 + 专家 review，原理完全一样：**专业提示词，是把专家的隐性知识前置到 prompt 里。**

## 8. 什么时候该用、什么时候不该用（Judgment）

**哪些情况该靠「专业能力 + 提示词」这条路？** 当你要用 AI 写**自己真正懂的领域**代码时——你清楚边界、知道该禁止什么、能判断对错。此时专业提示词能大幅放大你的效率，AI 是你的超级放大器。同样，当你面对**可复用、可验证**的任务时，用结构化提示词能显著降低返工率。

**哪些情况不该急着上 AI 写代码，或者不该只靠 AI？** 当你对某个领域**完全不了解**时，别幻想 AI 能替你「跳过学习」。你可以让 AI 帮你搭骨架、做 demo，但**核心逻辑、安全方案、业务意图必须由懂行的人把关**。另外，在**高风险、强审计**的场景（金融核心链路、涉及真实用户数据的后端），专家人工审查不可替代，AI 生成的代码必须过专家这一关才能上线。

**一句话判据**：**「懂行 + 可验证」才值得用 AI 放大效率；「不懂 + 高风险」先别碰，AI 救不了你。** 拼到最后拼的还是人，不是一句口号，是你在键盘前每敲一个 prompt 时的真实处境——先看自己懂不懂，再看任务风险高不高，再决定怎么用 AI。
