# AI 写前端界面堆满小字说明怎么办：一条 UI 降噪指令让布局自己解释

> **核心结论**：AI 给每个功能配一行小字，不是「细心」，而是**它没有可用的布局**——字段旁没有单位位、分组没有层级、控件不会自证用途，它只能用文字补。所以解法不是让它「少写点」，而是给文字设一道可判定的门槛：**能从布局读出来的信息，一律不许写成字**。本文给一条可直接粘进 `AGENTS.md` / `.cursor/rules` 的指令，配一个可运行的单文件 Demo：同一张表单，辅助文字 **11 处 → 2 处**、字数 **258 → 19**、面板高度 **1105 → 820 px**。

## 1. 一句话结论（Conclusion）

先看一个画面 🎭：你去看房，发现中介在**每件家具上贴了一张纸条**——沙发上写「这是沙发，用于坐」，灯上写「这是灯，晚上打开」，冰箱上写「冰箱，保鲜食物」。你不会觉得他细心，只会想：这房子是不是没布置好？

AI 写前端就是那个中介。它给昵称输入框底下写「昵称长度为 2–20 个字符」，给开关底下写「开启后可以接收通知」，给整个区块顶上写「以下信息将展示在你的个人主页」——每一句单看都没错，合起来就是**在客厅每件家具上贴纸条**。

所以记住这一句：

**AI 堆小字不是表达问题，是布局欠债；你越让它「写清楚」，它越用文字替布局还债。**

解法是把门槛写进规则：**能从布局（label、单位后缀、默认值、分组间距、控件形态）读出来的，禁止写成文字；只有「看不见的后果」和「必错的坑」才配占一行字。**

这个判断不是审美偏好。本专栏在 [12 种高级 UI 交互效果及对应 AI 提示词](https://juejin.cn/post/7704947965462315035) 里讲过同一条规律：AI 只认**具体、可判定的规格**，「加个动效」它给最普通的缩放，说「松手先弹到 1.05 再落回 1.0」它才照做。小字说明也是同一回事——你说「简洁一点」它听不懂，你说「辅助文字不得超过字段数，且只许三类」它立刻能执行。

## 2. AI 为什么爱给每个功能配一行小字（Root Cause）

三个原因叠加，缺一不可：

**① 训练语料里 helper text（辅助说明文字）就是标配。** 后台管理模板、SaaS 表单、Material 与 Bootstrap 的示例页，几乎每个 input 下面都有一行灰色小字。AI 学到的是「表单长这样」，而不是「表单该长这样」。

**② AI 是逐组件生成的，局部最优拼成全局噪声。** 它一次只盯一个字段：这个字段加一行说明，局部更清楚；那个开关加一行说明，局部也更清楚。但页面是**整体**阅读的，11 个局部最优拼起来，就是 11 个抢注意力的灰点。

**③ 写字的成本比调布局低一个数量级。** 要消掉「金额单位不清」，它得改结构（加后缀、改栅格、重排间距）；要消掉同一个问题，它只要写一句「单位：元」。AI 当然选便宜的那条路——这不是它懒，是**你从没告诉它贵的那条路更优先**。

用一句话收束：**AI 在用文字给布局打补丁。** 补丁越多，说明底下的布局越空。

## 3. 小字说明的三笔账（The Cost）

小字看起来「只占一行」，实际要付三笔账：

- **认知负荷（Cognitive Load）**：每一行灰字都是一个**新的阅读任务**。用户得先扫一眼、判断「这行跟我有没有关系」，再决定要不要读。11 行小字就是 11 次判断，而其中大多数判断的结论都是「跟我无关」。
- **视觉层级（Visual Hierarchy）**：小字通常和正文同色系、字号只差 1–2px。数量一多，它们就构成**第二正文**，把真正的正文（字段名、值、按钮）压成一片平均灰度，主次直接消失。
- **维护成本（Maintenance）**：文案会随业务漂移。一个字段改名，往往要同步改标题、改 label、改辅助说明、改错误提示四处；漏一处就是自相矛盾的界面。

前两笔是用户付的，第三笔是你付的。三笔账都在同一处产生：**这行字本来可以不出现在屏幕上。**

## 4. 一条判断标准：三问删字测试（Delete Test）

不用记设计原则，只对每一行辅助文字问三句：

1. **布局能不能表达？** 单位、必填、范围、默认行为——这些都能塞进 label 或输入框后缀，能塞进去的就别另起一行。
2. **用户会不会在这里停？** 只有「会犹豫」或「会填错」的地方才配常驻一行字。昵称、邮箱、手机号这类人人会填的字段，不需要解释。
3. **这行字是不是只有报错时才需要？** 是的话，把它移到校验提示里，**不要常驻**。

三问里只要有一个答案是「能 / 不会 / 是」，这行字就该删。

举个具体例子：「密码需至少 8 位，且包含字母与数字」——第 1 问：能塞进 label 吗？能，写成「新密码 ≥ 8 位，含字母与数字」。第 2 问：用户会停吗？会，这条要留。第 3 问：只在报错时需要吗？不是，提前说比事后报错好。结论：**留内容，删行数**——从独立一段降级为 label 里的后缀。

这就是本文强调的重点：**不是把字删干净，而是把字降级到它该在的层级。**

## 5. 让布局自己解释的五种手法（Affordance）

文字能待的位置只有四种：独立一段、label 后缀、输入框占位/后缀、默认值。越靠后越省空间，也越不打断阅读；第五种是**干脆不写**。五种手法按这个顺序用：

**① 单位进后缀。** 输入框右侧放 `元`、`kg`、`天`，比下面写「请输入金额，单位为元」省一整行。金额、重量、时长、百分比都适用。

**② 约束进 label。** 「昵称 2–20 字符」把规则和字段名放同一行，用户读字段名时顺手就读到了约束，不需要第二眼。

**③ 分组代替说明段。** 「基本信息 / 通知 / 安全」三个分组标题 + 分隔线，已经表达了「这是三类设置」。再补一句「以下信息将展示在你的个人主页」，属于把分组已经说完的话又说一遍。

**④ 默认值即说明。** 通知频率写成 `周一 09:00`，比「每周一上午 9 点发送」少一半字，还顺便展示了可编辑的形态。能让值自己说话的，别用句子。

**⑤ 控件自证用途。** 开关不需要解释「打开后可接收通知」——开关的形状已经说明了。下拉框不需要写「点击选择」——箭头已经说明了。**给控件写使用说明，是 AI 最典型的过度交付。**

## 6. 一条可直接用的 UI 降噪指令（Rule）

把下面这段原样粘进项目根的 `AGENTS.md`，或 `.cursor/rules/ui.mdc`（Cursor 的 rules 机制见 [官方文档](https://cursor.com/docs/rules)）。规则的价值在于**可判定**：每一条都能被数出来、被检查出来。

```markdown
## UI 文案密度规则

1. 辅助文字配额：每个字段最多 1 行辅助文字（含 label 后缀），
   全页辅助文字总条数 ≤ 字段数，且单条 ≤ 20 字。
2. 只允许三类辅助文字：
   - 格式约束（如「≥ 8 位，含字母与数字」）
   - 看不见的后果（如「保存后需重新登录」）
   - 易错提醒（如「身份证号末位 X 需大写」）
   其余一律删除。
3. 能从布局读出的信息，禁止写成文字：
   - 单位 → 输入框后缀
   - 范围/长度 → label 后缀
   - 分类关系 → 分组标题 + 分隔线，禁止补「以下信息将……」
   - 默认行为 → 直接把默认值写进控件
4. 禁止为下列元素写解释：按钮、开关、下拉框、单选框、图标。
5. 交付前自检：数一遍 .aux 节点数量与总字数，超出配额先删，不许改小字号蒙混。
```

第 5 条的「数一遍」是关键。**能被数出来的规则，AI 才会真的执行**；写成「保持简洁」「避免冗余」这种形容词，等于没写。

## 8. 对照实验：同一张表单两种写法（Comparison）

同一批字段、同一套 CSS 变量、同一个视口宽度，只改文案密度：

![版本 A：AI 默认产出，每个字段都配小字说明](https://raw.gitcode.com/ZhengEnCi/knoweledges/raw/master/resources/Q16/q16-panel-a-ai-default.png)

![版本 B：降噪后，只保留 2 处必要文字](https://raw.gitcode.com/ZhengEnCi/knoweledges/raw/master/resources/Q16/q16-panel-b-cleaned.png)

实测结果：

| 指标 | 版本 A（AI 默认） | 版本 B（降噪后） | 变化 |
|---|---|---|---|
| 辅助文字条数 | 11 条 | 2 条 | −82% |
| 辅助文字总字数 | 258 字 | 19 字 | −93% |
| 面板渲染高度 | 1105 px | 820 px | −26% |
| 字段数量 | 6 个 | 6 个 | 不变 |

这里有个容易被忽略的反差：**字数降了 93%，高度只降了 26%**。原因很简单——字段、输入框、按钮的高度是刚性的，小字挤占的是「行」，不是「控件」。删掉 9 行辅助文字，只腾出 285 px（1105 − 820），平均每行约 32 px。

所以别指望删字能把页面「变短一半」。**降噪的真正收益不在高度，而在阅读路径**：版本 A 的视线在「字段名 → 输入框 → 灰字 → 下一个字段名」之间来回跳 11 次，版本 B 只有 2 次。用户在 A 里每填一个字段，都要先判断底下那行灰字跟自己有没有关系；在 B 里，填完就走。

这也是为什么「把字号调到 11px、颜色再灰一点」不是解法——**问题不是小字太显眼，而是它根本不该在那**。

## 9. 什么时候必须留字（Progressive Disclosure）

降噪不是把字删光。有四类信息**必须常驻**，因为它们无法从布局推出：

1. **看不见的后果**：「删除后不可恢复」「保存后需重新登录」——后果发生在点击之后，界面本身无法预告。
2. **无自然占位的格式约束**：身份证号、税号、自定义编码，没有单位可用、没有默认值可展示。
3. **高风险输入**：金额、权限、批量操作，错一次代价高，值得占一行字。
4. **合规与法律文案**：这类文字有留存要求，不属于设计决策。

其余信息可以用 [渐进式披露（Progressive Disclosure）](https://www.nngroup.com/articles/progressive-disclosure/) 的思路处理：**默认只展示当前决策必需的信息，把细节放到用户主动索取的位置**（展开更多、悬停提示、失焦后的校验提示、帮助中心）。这条模式的核心是「先给最重要的，其余的按需呈现」，正好对治 AI 的「一次全给」。

注意边界：渐进式披露不等于把字藏起来。**该在填写前说清的约束，不能挪到报错后**——「密码 8 位以上」写在 label 里是提示，只写在错误提示里就是惩罚。

## 10. 对照表：症状 → 原因 → 解法（Symptom → Cause → Fix）

| 症状 | 原因 | 解法 |
|---|---|---|
| 每个字段下都有一行灰字 | 训练语料默认带 helper text，逐组件生成时局部最优 | 规则里写死配额：辅助文字 ≤ 字段数，单条 ≤ 20 字 |
| 每个区块顶上都有一段说明 | 分组标题缺失，只能用段落交代分类 | 补分组标题 + 分隔线，删段落 |
| 开关、按钮旁边有使用说明 | AI 把「解释控件」当成负责任 | 规则里列黑名单：按钮/开关/下拉/单选/图标禁止配文字 |
| 单位、范围、格式散落在小字里 | 没有用后缀与 label 承载约束 | 单位进后缀，约束进 label 后缀 |
| 界面「说得很全但很难用」 | 文字替代了层级、间距与默认值的设计 | 先改布局（分组/后缀/默认值），再决定留哪几行字 |
| 改一次文案要动五处 | 同一条信息在标题、label、说明、错误提示里重复 | 信息只保留一处来源，其余位置引用或删除 |

## 11. 落地顺序：四步验收（Rollout）

1. **贴规则**：把第 6 节那段贴进 `AGENTS.md` 或 `.cursor/rules/ui.mdc`。规则要在**生成前**生效，事后改文案的成本高十倍。
2. **重新生成**：让 AI 按规则重出这一页，而不是自己手动删。手动删只能修一页，规则能修之后的每一页。
3. **跑自检**：用第 7 节的 `stat()` 数一遍条数与字数，超配额就打回。这一步必须由机器算，肉眼数不准。
4. **人工删字测试**：对剩下的每一行问第 4 节那三问，能降级到 label 的就降级，能挪到校验提示的就挪。

验收标准只有一条：**把辅助文字全部遮住，页面还能不能读懂？** 能读懂的部分，文字就是装饰；读不懂的部分，才需要补布局，而不是补文字。

一条规则能在生成前拦住大部分噪声，却拦不住「该写却没写」。真正决定界面质感的，仍然是你对「哪些事必须说、哪些事布局自己会说」的判断。

判断收尾：如果你在做还在长功能的产品页面，先把降噪规则贴进 `AGENTS.md` 再让 AI 动手；如果是一次性营销页、文案本身就是卖点，这套配额要放宽，别为了干净把说服力删掉。
