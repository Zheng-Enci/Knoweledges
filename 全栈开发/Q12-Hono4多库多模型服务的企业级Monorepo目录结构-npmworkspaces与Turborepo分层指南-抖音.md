## P01 · 封面

> 卡片职责：抛钩子 + 定锚主题，点破「Monorepo 目录」核心名词

- **企业级 Monorepo 目录到底怎么放？**
- 不是按 utils / service / db 分，是按「谁跟谁一起变」分
- **4 层**单向依赖：apps → features → adapters → core
- 4 个库 + 7 家模型，全靠这套骨架收住

## P02 · 分包按变化原因不按技术名词

> 卡片职责：给判断标准，纠正最常见的分错方式

- 按技术名词分会得到三个巨型文件夹，谁都能往里面丢东西，半年后没人敢删。
- 正确的问法是：这两个文件会不会**一起改**，一起改的放一起，分开改的拆开。
- MySQL 的 schema 和 Milvus 的 collection 几乎永不一起改，所以必须是**两个包**。
- 模型参数差异和 HTTP 客户端天天一起改，所以它们属于**同一个包** 🎯。

## P03 · 五个顶层目录各管一件事

> 卡片职责：给全貌骨架，建立分层印象

- apps 放可部署单元，每个目录对应一个 PM2 进程，是门店。
- packages/features 放跨 adapter 的业务编排，是**中央厨房**，门店可以点菜。
- packages/adapters 放数据库、向量库、模型、浏览器的适配，是**供应链** 🚚。
- packages/core 放实体与端口接口，是**菜谱**，零 IO，谁都不能反向指挥 🍳。
- contracts 和 utils 是叶子包，没有内部依赖，谁引用都安全 ✅。

## P04 · apps 只做装配逻辑全下沉

> 卡片职责：讲 apps 层边界，最容易被写胖的一层

- 一个 app 里只该有四类文件：入口、容器、路由、中间件，多一类都值得怀疑。
- container.ts 是**唯一开关**，多库多模型的判断全部收敛在这一个文件里。
- 路由层薄到只剩映射：解析参数、调 feature、返回结果，不写业务判断。
- 反直觉取舍：apps **只写 e2e 测试不写单测**，给装配代码写单测等于测 new 关键字。
- e2e 用 app.request() 直接打 Hono 实例，不启端口，比起服务器快一个数量级 ⚡。

## P05 · core 是零 IO 的领域内核

> 卡片职责：讲最硬的一条边界，说明它为什么值钱

- core 里不许有 fs、不许有 fetch、不许有 ORM、不许有 process.env，只留类型和接口。
- 端口接口让「换数据库」「加第八家模型」变成加一个实现，而不是改业务代码。
- 用例测试塞一个假实现就能跑，不需要数据库也不需要 API Key。
- 守边界靠工具不靠评审：用 ESLint 的 no-restricted-imports 直接把 **drizzle-orm 禁掉** 🔒。
- 一旦有人在 core 里 import ORM，整个包就锁死在 ORM 上，之后换方言都得改业务代码 ⚠️。

## P06 · 四个库不能共用一份 schema

> 卡片职责：讲多方言最容易崩的地方，给可复现症状

- Drizzle 是方言绑定的，自增主键三个库三种写法：autoincrement、serial、integer。
- 时间字段也不一样：MySQL 是 timestamp，PG 是 timestamptz，SQLite 是 integer 🔪。
- 想用一份 schema 驱动三个方言，最后一定在迁移阶段崩，报的还是 **Unknown column**。
- 正确做法是共享领域实体和 Repository 接口，**各自维护方言 schema** 与独立迁移目录。
- 三个仓库实现看起来重复，这是**可接受的重复**：方言差异客观存在，藏起来迟早爆 💡。

## P07 · 七家模型就是一个包七份配置

> 卡片职责：讲 AI 层收口，回答「要不要写七个包」

- 七家全走 OpenAI 兼容协议，共用一个 HTTP 客户端，差异只写在七份 **ProviderConfig** 里。
- 七份配置加起来不到 100 行，剩下 300 行通用逻辑只写一遍，维护成本直接降一个量级 ✅。
- 隐蔽陷阱：兼容的是接口路径，不是参数语义，推理模型的回复在 reasoning_content 里。
- 所以差异全部收在 openai-compat.ts，对外只暴露 chat 和 embed 两个方法。
- API Key 不进包，由 app 的 env 注入，这样 ai 包在任何 app 里都能复用 🔑。

## P08 · 浏览器进程单例指纹要前置

> 卡片职责：讲 Playwright 摆放，两条最容易错的顺序

- 核心矛盾只有一个：**指纹要隔离，但浏览器进程要复用**，所以进程单例、context 每任务一个。
- 起一个 Chromium 要几百毫秒和上百 MB，起一百个直接把机器打爆 📉。
- 指纹注入必须在 page.goto **之前**，否则页面脚本早把 navigator.webdriver 读走了。
- 站点流程和指纹分离：flows 只写点哪里，profiles 才写 userAgent，互不牵连。
- 这个包**绝不能跑 cluster**，8 核机器就是 8 个浏览器常驻，内存直接见底 🚨。

## P09 · PM2 cluster 只留给 HTTP 服务

> 卡片职责：讲进程边界，给出可复制的配置判据

- HTTP 服务可以 cluster，浏览器和定时任务不行，这条要写进部署注释。
- worker 和 scheduler 必须显式写 exec_mode 为 fork、instances 为 1 ⚙️。
- 隐性理由：定时任务在多进程下会**重复派发**，不加分布式锁就只能单实例。
- 并发不靠进程数，靠内部队列控制，扩容时先想清楚哪一层能横向扩。
- 目录结构靠文档约定一周就失效，唯一可靠的办法是把它变成一条 **CI 命令** 🔒。

## P10 · 判断收尾 + 互动钩子

> 卡片职责：给判据式结论 + 唯一一句互动钩子

- 判断标准：**团队超过三人，或者有第二个部署单元要共享领域逻辑**，这套结构才回本。
- 该上：多数据库、多模型、多部署单元同时存在，收益立刻出来 ✅。
- 不必上：单人项目、只有一个 app、只有一套库，建 Monorepo 只是给 import 加前缀。
- 一句话收束：**反向依赖不该靠口头约定，该靠一条会退出码为 1 的脚本** ⚖️。
