# 用户签字功能前后端实现与存储方案

本文档系统讲解 Web 应用中用户电子签字（Electronic Signature）功能的完整实现方案，涵盖前端 Canvas 签名捕获、后端 Spring Boot 签名处理，以及签字信息的存储策略。通过理论与实践结合的方式，帮助开发者快速搭建一套可用的电子签字功能 🛠️
<!-- English Abstract -->

This document systematically explains the complete implementation of an electronic signature feature in web applications, covering frontend Canvas-based signature capture, backend Spring Boot signature processing, and signature data storage strategies. It helps developers quickly build a production-ready e-signature feature through theory and practice 🛠️

## 术语表 / Terminology

| 术语 / Term        | 说明 / Description                                            |
| ------------------ | ------------------------------------------------------------- |
| **Canvas**         | HTML5 提供的位图绘制 API，用于在浏览器中实时绘制签名          |
| **Base64**         | 将二进制数据编码为 ASCII 字符串的编码方式，常用于传输图片数据 |
| **Data URL**       | 将图片数据嵌入 URL 中的格式（`data:image/png;base64,...`）    |
| **Bézier Curve**   | 贝塞尔曲线，用于使 Canvas 绘制的签名线条更平滑                |
| **Multipart File** | HTTP 多部分文件上传协议，Spring Boot 中用于接收文件上传       |
| **BLOB**           | Binary Large Object，数据库中存储大量二进制数据的字段类型     |
| **BYTEA**          | PostgreSQL 中存储二进制数据的类型（类似 BLOB）                |
| **Audit Trail**    | 审计追踪，记录签字操作的时间、IP、设备等元数据                |
| **LOB**            | Large Object，数据库中用于存储大字段数据的抽象概念            |
| **MultipartFile**  | Spring 框架中用于接收上传文件的接口                           |

## 1. 环境准备 🧰 / Environment Setup

### 1.1 前端依赖 / Frontend Dependencies

前端签字功能基于原生 HTML5 Canvas API，**无需额外 JavaScript 库即可实现核心功能**。但如需更平滑的签名体验，可选用以下开源库：

- **signature_pad** ✍️：基于 Canvas 的签名绘制库，支持可变宽度 Bézier Curve 插值，生成的签名线条更自然流畅。可通过 npm 安装或直接引入 CDN。
- **原生 Canvas API** 🖌️：如果项目对依赖管理有严格要求，完全可以使用原生 Canvas + 原生 Touch/Mouse Events 实现。核心 API 仅需 `canvas.getContext('2d')` 和 `canvas.toDataURL()` 两个方法。

推荐方案：初学者先用原生 Canvas 理解核心原理，项目中使用 signature_pad 提升开发效率和用户体验。


## 2. 前端签字实现 🎨 / Frontend Signature Implementation

> 🎨 **Note:** 本章讲解如何用 HTML5 Canvas 搭建签名板，包括事件处理、绘制逻辑与数据导出 / This chapter explains how to build a signature pad using HTML5 Canvas, including event handling, drawing logic, and data export.

前端签字功能的核心原理是：**在 Canvas 上监听用户的鼠标/触摸事件，实时绘制笔迹，最后将绘制内容导出为图片（Base64 Data URL 或 Blob）上传到后端**。

### 2.1 Canvas 签名板基础结构 / Basic Canvas Signature Pad

首先搭建签名板的 HTML 结构：

```html
<!-- 签名板容器，用于布局控制 -->
<div class="signature-container">
    <!-- 签名标题提示 -->
    <label>请在下⽅签名：</label>
    <!-- Canvas 签名区域：设置宽⾼确保签名有⾜够空间 -->
    <canvas id="signatureCanvas" width="500" height="200"
            style="border: 1px solid #ccc; touch-action: none;">
        您的浏览器不支持 Canvas
    </canvas>
    <!-- 操作按钮区：清除签名与确认提交 -->
    <div class="signature-actions">
        <button id="clearBtn">清除</button>
        <button id="saveBtn">确认签名</button>
    </div>
</div>
```

> 💡 **注意**：`touch-action: none` 是关键——它阻止浏览器在触摸 Canvas 时触发默认滚动行为，确保签名绘制不会被页面滚动干扰。

### 2.2 鼠标事件处理 / Mouse Event Handling

鼠标输入是签名板的基础交互方式，需要监听三个核心事件：

```javascript
// 获取 Canvas 元素与 2D 绘图上下⽂
const canvas = document.getElementById('signatureCanvas');    // 获取 Canvas DOM 元素
const ctx = canvas.getContext('2d');                         // 获取 2D 绘图上下⽂

let isDrawing = false;   // 当前是否正在绘制
let lastX = 0, lastY = 0; // 上⼀个点的坐标

// 配置画笔样式
ctx.strokeStyle = '#000000';   // 画笔颜⾊：⿊⾊
ctx.lineWidth = 2;             // 线条宽度：2px
ctx.lineCap = 'round';         // 线条端部：圆形
ctx.lineJoin = 'round';        // 线条连接处：圆形

/* 获取⿏标在 Canvas 内的相对坐标
 *
 * 参数 / Args:
 *   e: ⿏标事件对象
 *   canvas: Canvas DOM 元素
 *
 * 返回 / Returns:
 *   {x, y} 相对坐标
 *
 * 示例 / Example:
 *   mousePos = getMousePos(event, canvas) → {x: 150, y: 80}
 */
function getMousePos(e, canvas) {
    const rect = canvas.getBoundingClientRect();  // 获取 Canvas 的边界矩形，示例：rect={left:100, top:50}
    return {
        x: e.clientX - rect.left,                // 计算相对 x：clientX - canvas 左边距
        y: e.clientY - rect.top                   // 计算相对 y：clientY - canvas 上边距
    };
}

// ⿏标按下：开启绘制模式
canvas.addEventListener('mousedown', (e) => {
    isDrawing = true;                             // 开启绘制
    const pos = getMousePos(e, canvas);           // 获取⿏标坐标，示例：{x: 150, y: 80}
    lastX = pos.x;                                // 记录起点 x
    lastY = pos.y;                                // 记录起点 y
});

// ⿏标移动：在绘制模式下画线
canvas.addEventListener('mousemove', (e) => {
    if (!isDrawing) return;                        // ⓪ 未绘制则直接返回
    const pos = getMousePos(e, canvas);            // 获取当前⿏标坐标
    ctx.beginPath();                               // ① 开始新路径
    ctx.moveTo(lastX, lastY);                      // ② 移动到上⼀个点
    ctx.lineTo(pos.x, pos.y);                      // ③ 绘制到当前点
    ctx.stroke();                                  // ④ 执⾏描边
    lastX = pos.x;                                 // ⑤ 更新上⼀个点 x
    lastY = pos.y;                                 // ⑥ 更新上⼀个点 y
});

// ⿏标释放：关闭绘制模式
canvas.addEventListener('mouseup', () => {
    isDrawing = false;                             // 关闭绘制
});

// ⿏标离开 Canvas：关闭绘制模式（防⽌⿏标移出 Canvas 后线条断掉）
canvas.addEventListener('mouseleave', () => {
    isDrawing = false;                             // ⿏标离开时关闭绘制
});
```

**数据流动示例** 📊：

```
用户⿏标按下 (mousedown) → isDrawing=true, lastPos={x:50, y:30}
       ↓
用户拖动⿏标 (mousemove) → 每帧在 lastPos 到 currentPos 之间画线
       ↓
用户释放⿏标 (mouseup) → isDrawing=false
```

### 2.3 触摸事件处理 / Touch Event Handling

移动端需要 Touch Events 来替代 Mouse Events。核心区别是：Touch Events 的坐标需要通过 `e.touches[0]` 获取，且需要 `e.preventDefault()` 阻止滚动：

```javascript
/* 获取触摸点在 Canvas 内的相对坐标
 *
 * 参数 / Args:
 *   e: 触摸事件对象
 *   canvas: Canvas DOM 元素
 *
 * 返回 / Returns:
 *   {x, y} 相对坐标
 */
function getTouchPos(e, canvas) {
    const rect = canvas.getBoundingClientRect();  // 获取 Canvas 边界矩形
    const touch = e.touches[0];                   // 获取第⼀个触摸点
    return {
        x: touch.clientX - rect.left,            // 计算相对 x：触摸点 x - canvas 左边距
        y: touch.clientY - rect.top               // 计算相对 y：触摸点 y - canvas 上边距
    };
}

// 触摸开始：开启绘制
canvas.addEventListener('touchstart', (e) => {
    e.preventDefault();                           // 阻⽌⻚⾯滚动
    const pos = getTouchPos(e, canvas);           // 获取触摸坐标
    lastX = pos.x;                                // 记录起点 x
    lastY = pos.y;                                // 记录起点 y
    isDrawing = true;                             // 开启绘制
});

// 触摸移动：连续绘制
canvas.addEventListener('touchmove', (e) => {
    e.preventDefault();                           // 阻⽌⻚⾯滚动
    if (!isDrawing) return;                       // 未绘制则返回
    const pos = getTouchPos(e, canvas);           // 获取当前触摸坐标
    ctx.beginPath();                              // 开始新路径
    ctx.moveTo(lastX, lastY);                     // 移动到上⼀个点
    ctx.lineTo(pos.x, pos.y);                     // 绘制到当前点
    ctx.stroke();                                 // 执⾏描边
    lastX = pos.x;                                // 更新上⼀个点
    lastY = pos.y;
});

// 触摸结束：关闭绘制
canvas.addEventListener('touchend', (e) => {
    e.preventDefault();                           // 阻⽌默认⾏为
    isDrawing = false;                            // 关闭绘制
});
```

> ⚠️ **Key Point**：`e.preventDefault()` 在这⾥⾮常重要——如果不调⽤，⽤户在⼿机上签名时⻚⾯会跟随⼿指滚动，导致签名线条断断续续。

### 2.4 清除与导出 / Clear and Export

**清除签名**：将 Canvas 重置为空白。比 `clearRect` 更可靠的方式是直接重置 Canvas 的 width（会连带清除 context 状态）：

```javascript
/* 清除 Canvas 上的所有内容
 *
 * 示例 / Example:
 *   clearCanvas() → Canvas 恢复为完全透明
 */
function clearCanvas() {
    ctx.clearRect(0, 0, canvas.width, canvas.height);  // 清除整个画布
}
```

**导出签名为 Base64 Data URL** 🔄：这是最常用的方式，将 Canvas 内容编码为 Base64 字符串，可以直接作为 JSON 字段发送给后端：

```javascript
/* 将签名导出为 Base64 Data URL
 *
 * 参数 / Args:
 *   format: 图片格式，默认 'image/png'
 *   quality: 图片质量（仅 JPEG/WebP 有效），0-1
 *
 * 返回 / Returns:
 *   dataURL字符串，示例："data:image/png;base64,iVBORw0KGgo..."
 *
 * 示例 / Example:
 *   const dataUrl = exportSignature()
 *   // → "data:image/png;base64,iVBORw0KGgoAAAANSUhEUg..."
 */
function exportSignature(format = 'image/png', quality = 0.92) {
    return canvas.toDataURL(format, quality);     // 将 Canvas 导出为 Base64 编码的 URL
}
```

**导出为 Blob 对象** 📦：适合通过 `multipart/form-data` 上传到后端：

```javascript
/* 将签名导出为 Blob 并通过回调返回
 *
 * 参数 / Args:
 *   callback: 接收 Blob 的回调函数
 *   format: 图片格式，默认 'image/png'
 *   quality: 图片质量（仅 JPEG/WebP 有效），0-1
 *
 * 示例 / Example:
 *   exportSignatureBlob((blob) => {
 *     const formData = new FormData();
 *     formData.append('signature', blob, 'signature.png');
 *   })
 */
function exportSignatureBlob(callback, format = 'image/png', quality = 0.92) {
    canvas.toBlob((blob) => {                     // Canvas.toBlob 异步返回 Blob
        callback(blob);                           // 回调中获取 Blob 对象
    }, format, quality);
}
```

### 2.5 提交签名到后端 / Submit Signature to Backend

拿到签名数据后，通过 AJAX 发送到后端。这里展示两种常见的传输方式：

**方式一：Base64 JSON（推荐用于简单场景）** 📤：

```javascript
/* 通过 JSON 提交 Base64 签名数据
 *
 * 数据流动 / Data flow:
 *   Canvas签名 → toDataURL() → Base64字符串 → JSON → POST /api/signatures → 后端
 */
async function submitSignatureBase64() {
    const signatureData = exportSignature();       // 获取 Base64 数据，示例："data:image/png;base64,iVBORw..."
    
    const response = await fetch('/api/signatures', {
        method: 'POST',                           // HTTP POST
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({                    // JSON 请求体
            documentId: 1001,                     // 文档 ID
            signatureData: signatureData,          // 签名 Base64 数据
            signerName: '张三',                    // 签字⼈姓名
            deviceInfo: navigator.userAgent        // 设备信息（审计追踪⽤）
        })
    });
    
    if (response.ok) {
        alert('签名提交成功！');                    // 提交成功提示
    }
}
```

**方式二：FormData Multipart（适合大文件）** 📎：

```javascript
/* 通过 FormData 提交签名 Blob
 *
 * 数据流动 / Data flow:
 *   Canvas签名 → toBlob() → Blob → FormData → POST /api/signatures/upload → 后端
 */
async function submitSignatureMultipart() {
    const formData = new FormData();               // 创建 FormData 对象
    
    exportSignatureBlob((blob) => {                // 导出为 Blob
        formData.append('file', blob, 'signature.png');    // 添加签名文件
        formData.append('documentId', '1001');     // 添加文档 ID
        formData.append('signerName', '张三');      // 添加签字⼈姓名
    });
    
    const response = await fetch('/api/signatures/upload', {
        method: 'POST',                           // HTTP POST
        body: formData                            // multipart/form-data 请求体
    });
}
```

### 2.6 使用 signature_pad 库简化开发 / Using signature_pad Library

如果不想从零实现，可以直接使用成熟的 signature_pad 库。它内置了可变宽度 Bézier 曲线插值，生成的签名更自然：

```javascript
// 如果通过 CDN 引⼊：SignaturePad 是全局变量
// 如果通过 npm 安装：import SignaturePad from 'signature_pad';

const canvas = document.getElementById('signatureCanvas');  // 获取 Canvas 元素
const signaturePad = new SignaturePad(canvas, {              // 创建 SignaturePad 实例
    penColor: '#000000',    // 笔迹颜⾊
    backgroundColor: '#ffffff', // 背景⾊
    minWidth: 0.5,          // 最小线条宽度（压感相关）
    maxWidth: 2.5           // 最⼤线条宽度
});

// 清除签名
function clearSignature() {
    signaturePad.clear();
}

// 判断签名是否为空
function isSignatureEmpty() {
    return signaturePad.isEmpty();    // 返回 true/false
}

// 导出 Base64
const dataUrl = signaturePad.toDataURL('image/png');
```

> 💡 **为什么 signature_pad 的签名更平滑？** 它使⽤了 Catmull-Rom 曲线插值，在⽤户的采样点之间插⼊平滑过渡，⽽不是简单的点对点直线连接，因此线条看起来更⾃然。

## 3. 后端签字处理 ⚙️ / Backend Signature Processing

> ⚙️ **Note:** 本章讲解 Spring Boot 后端如何接收前端提交的签字数据、进⾏校验和处理 / This chapter explains how the Spring Boot backend receives, validates, and processes signature data from the frontend.

后端签字处理的核心流程分为三步：**接收数据** → **校验数据** → **持久化存储**。根据前端传输方式的不同，后端有两种接收策略。

### 3.1 Base64 JSON 方式接收 / Receiving via Base64 JSON

前端通过 JSON 提交 Base64 Data URL 时，后端的 Controller 和 Service 设计如下：

```java
package com.example.signature.controller;

import com.example.signature.dto.SignatureRequest;           // 签字请求 DTO
import com.example.signature.service.SignatureService;       // 签字业务 Service
import lombok.RequiredArgsConstructor;                        // 构造器注入注解
import org.springframework.http.ResponseEntity;              // HTTP 响应实体
import org.springframework.web.bind.annotation.*;            // Web 注解

/**
 * 签字功能 REST Controller 🌐
 *
 * 提供签字数据的接收、查询等 API 接口
 */
@RestController                                                // RESTful Controller 注解
@RequestMapping("/api/signatures")                             // 请求基础路径：/api/signatures
@RequiredArgsConstructor                                       // 构造器注入，替代 @Autowired
public class SignatureController {

    private final SignatureService signatureService;           // 注入签字 Service

    /**
     * 提交签字数据（Base64 JSON 方式）📤
     *
     * 数据流动 / Data flow:
     *   前端 JSON → SignatureRequest DTO → SignatureService → 数据库
     *
     * 参数 / Args:
     *   request: 签字请求 DTO，包含 documentId、signatureData(base64)、signerName、deviceInfo
     *
     * 返回 / Returns:
     *   ResponseEntity: 包含创建的 Signature ID 和成功状态
     */
    @PostMapping                                                // POST /api/signatures
    public ResponseEntity<SignatureResponse> submitSignature(
            @RequestBody SignatureRequest request) {            // 接收 JSON 请求体
        
        SignatureResponse response = signatureService           // 调⽤ Service 处理签字
                .processSignature(request);                     // 处理并返回响应
        
        return ResponseEntity.ok(response);                     // 返回 200 OK 响应
    }
}
```

**SignatureRequest DTO** 📦：

```java
package com.example.signature.dto;

import lombok.Data;                                            // 生成 Getter/Setter/ToString 等

/**
 * 签字请求 DTO 📨
 *
 * 前端提交签字数据的数据传输对象
 */
@Data                                                          // Lombok ⾃动生成 Getter/Setter
public class SignatureRequest {
    private Long documentId;                                   // 关联的⽂档 ID
    private String signatureData;                               // 签名 Base64 数据，示例："data:image/png;base64,iVBORw0KGgo..."
    private String signerName;                                 // 签字⼈姓名
    private String deviceInfo;                                 // 设备信息（⽤于审计追踪，可选）
}
```

**SignatureResponse DTO** 📤：

```java
package com.example.signature.dto;

import lombok.AllArgsConstructor;                               // 全参构造器
import lombok.Data;                                            // 生成 Getter/Setter

/**
 * 签字响应 DTO 📨
 *
 * 返回给前端的签字结果
```

### 3.3 Service 层：Base64 解码与校验 / Service Layer: Base64 Decoding & Validation

```java
package com.example.signature.service;

import com.example.signature.dto.SignatureRequest;             // 签字请求 DTO
import com.example.signature.dto.SignatureResponse;            // 签字响应 DTO
import com.example.signature.entity.Signature;                  // 签字实体
import com.example.signature.repository.SignatureRepository;    // 签字 Repository
import lombok.RequiredArgsConstructor;                          // 构造器注入
import org.springframework.stereotype.Service;                  // Service 注解
import org.springframework.transaction.annotation.Transactional; // 事务注解
import org.springframework.web.multipart.MultipartFile;        // ⽂件上传接⼝

import java.time.LocalDateTime;                                // 本地⽇期时间
import java.util.Base64;                                       // Base64 编解码

/**
 * 签字业务 Service ⚙️
 *
 * 负责签字数据的业务处理，包括 Base64 解码、文件处理与持久化
 */
@Service                                                        // Service 层注解
@RequiredArgsConstructor                                        // 构造器注入
@Transactional                                                  // 开启事务管理
public class SignatureService {

    private final SignatureRepository signatureRepository;     // 签字 Repository
    private final SignatureFileStorageService fileStorageService; // ⽂件存储 Service

    /**
     * 处理 Base64 JSON 提方式的签字请求 📤
     *
     * 数据流动 / Data flow:
     *   Base64字符串 → 解码 → byte[] → 校验 → Signature实体 → 存储 → SignatureResponse
     *
     * 参数 / Args:
     *   request: 签字请求 DTO
     *
     * 返回 / Returns:
     *   SignatureResponse: 包含签字记录 ID
     */
    public SignatureResponse processSignature(SignatureRequest request) {
        // 1. 校验 Base64 数据是否为空
        if (request.getSignatureData() == null || request.getSignatureData().isBlank()) {
            throw new IllegalArgumentException("签字数据不能为空");  // 抛出异常，由全局异常处理捕获
        }
        
        // 2. 从 Data URL 中提取纯 Base64 字符串
        // 数据流动 / Data flow:
        //   "data:image/png;base64,iVBORw0KGgo..." → "iVBORw0KGgo..."
        String base64Data = extractBase64Data(request.getSignatureData());
        
        // 3. Base64 解码为字节数组
        byte[] imageBytes = Base64.getDecoder().decode(base64Data);   // 解码，数据流动：String → byte[]
        
        // 4. 构建 Signature 实体并存储
        Signature signature = new Signature();
        signature.setDocumentId(request.getDocumentId());              // 设置文档 ID
        signature.setSignerName(request.getSignerName());              // 设置签⼈姓名
        signature.setDeviceInfo(request.getDeviceInfo());              // 设置设备信息
        signature.setSignatureData(imageBytes);                        // 设置签名字节数据
        signature.setCreatedAt(LocalDateTime.now());                   // 设置创建时间
        
        // 5. 持久化到数据库
        Signature saved = signatureRepository.save(signature);        // 保存签字记录
        
        // 6. 返回响应
        return new SignatureResponse(saved.getId(), "签字提交成功");
    }
    
    /**
     * 从 Data URL 中提取纯 Base64 字符串 🔧
     *
     * 参数 / Args:
     *   dataUrl: 完整的数据 URL，示例："data:image/png;base64,iVBORw0KGgo..."
     *
     * 返回 / Returns:
     *   纯 Base64 字符串，不含前缀
     *
     * 示例 / Example:
     *   extractBase64Data("data:image/png;base64,ABC123") → "ABC123"
     */
    private String extractBase64Data(String dataUrl) {
        // 按逗号分割，取后半部分（纯 Base64 编码数据）
        // 示例：split(",") → ["data:image/png;base64", "iVBORw0KGgo..."]
        if (dataUrl.contains(",")) {                                  // 判断是否包含逗号
            return dataUrl.split(",")[1];                            // 返回 Base64 数据部分
        }
        return dataUrl;                                                // 如果没有逗号，直接返回原始字符串
    }
    
    /**
     * 处理 MultipartFile 文件上传方式的签字 📎
     *
     * 参数 / Args:
     *   file: 上传的签名文件
     *   documentId: 关联文档 ID
     *   signerName: 签字⼈姓名
     *
     * 返回 / Returns:
     *   SignatureResponse: 包含签字记录 ID
     */
    public SignatureResponse processSignatureFile(
            MultipartFile file, Long documentId, String signerName) {
        
        // 1. 校验文件是否为空
        if (file.isEmpty()) {
            throw new IllegalArgumentException("签字文件不能为空");
        }
        
        try {
            // 2. 读取文件字节
            byte[] imageBytes = file.getBytes();                      // MultipartFile → byte[]
            
            // 3. 构建 Signature 实体
            Signature signature = new Signature();
            signature.setDocumentId(documentId);                      // 设置文档 ID
            signature.setSignerName(signerName);                      // 设置签字⼈姓名
            signature.setDeviceInfo(file.getContentType());           // 记录文件类型
            signature.setSignatureData(imageBytes);                   // 设置签名字节数据
            signature.setCreatedAt(LocalDateTime.now());              // 设置创建时间
            
            // 4. 持久化
            Signature saved = signatureRepository.save(signature);
            
            return new SignatureResponse(saved.getId(), "签字文件上传成功");
            
        } catch (Exception e) {
            throw new RuntimeException("签字文件处理失败: " + e.getMessage());
        }
    }
}
```

## 4. 签字信息存储方案 💾 / Signature Storage Strategy

> 💾 **Note:** 本章分析三种主流签字存储方案及其优缺点，并给出选型建议 / This chapter analyzes three mainstream signature storage strategies with their pros and cons, and provides selection recommendations.

签字的存储是整个功能的数据基石，直接影响**查询性能**、**数据安全**和**合规性**。目前主流方案有三种：数据库直接存储（BLOB）、文件系统存储、以及混合存储。

### 4.1 方案一：数据库 BLOB 存储 / Option 1: Database BLOB Storage

**原理**：将签名图片的二进制数据直接存入数据库字段。

**JPA Entity 设计** 📋：

```java
package com.example.signature.entity;

import jakarta.persistence.*;                                       // JPA 注解
import lombok.Data;                                                 // Lombok ⾃动生成
import java.time.LocalDateTime;                                     // ⽇期时间

/**
 * 签字记录实体 📝
 *
 * 存储签字数据及其元信息
 */
@Entity                                                            // JPA 实体注解
@Table(name = "signatures")                                         // 映射到 signatures 表
@Data                                                              // Lombok ⾃动生成 Getter/Setter
public class Signature {

    @Id                                                             // 主键
    @GeneratedValue(strategy = GenerationType.IDENTITY)             // ⾃增主键
    private Long id;                                                // 签字记录 ID

    @Column(name = "document_id", nullable = false)                 // ⽂档 ID，⾮空
    private Long documentId;                                        // 关联的⽂档 ID

    @Column(name = "signer_name", nullable = false)                // 签字⼈姓名，⾮空
    private String signerName;                                      // 签字⼈姓名

    @Lob                                                            // ⼤字段注解，PostgreSQL 映射为 OID
    @Column(name = "signature_data", columnDefinition = "BYTEA")  // 签字⼆进制数据
    private byte[] signatureData;                                   // 签名字节数组

    @Column(name = "device_info")                                  // 设备信息
    private String deviceInfo;                                      // 设备 User-Agent、IP 等

    @Column(name = "signer_ip")                                    // 签字⼈ IP 地址
    private String signerIp;                                        // 记录签字时的 IP

    @Column(name = "created_at", nullable = false, updatable = false) // 创建时间，不可更新
    private LocalDateTime createdAt;                                // 签字时间
}
```

> ⚠️ **注意**：在 PostgreSQL 中，`@Lob` 默认映射为 OID（Large Object），而 `columnDefinition = "BYTEA"` 强制使用 BYTEA 类型。**两者不能混用**——如果使用 BYTEA，建议去掉 `@Lob`，仅保留 `@Column(columnDefinition = "BYTEA")`。对于 1MB 以下的签字图片，BYTEA 性能更佳。

**数据库表结构** 🏗️：

```sql
CREATE TABLE signatures (
    id              BIGSERIAL PRIMARY KEY,            -- ⾃增主键
    document_id     BIGINT NOT NULL,                  -- ⽂档 ID
    signer_name     VARCHAR(100) NOT NULL,            -- 签字⼈姓名
    signature_data  BYTEA NOT NULL,                   -- 签字⼆进制数据
    device_info     VARCHAR(500),                     -- 设备信息
    signer_ip       VARCHAR(45),                      -- 签字⼈ IP（⽀持 IPv6）
    created_at      TIMESTAMP NOT NULL DEFAULT NOW()  -- 签字时间
);

-- 创建索引加速查询
CREATE INDEX idx_signatures_document_id ON signatures(document_id);  -- ⽂档查询索引
CREATE INDEX idx_signatures_created_at ON signatures(created_at);   -- 时间范围查询索引
```

**✅ 优点**：
- 数据完整性强：签字与业务数据在同一数据库，备份、恢复方便
- 事务一致：签字写入与业务更新可在同一事务中完成
- 访问控制简单：数据库权限天然管控

**❌ 缺点**：
- 数据库体积膨胀快，备份大小激增
- 查询性能随数据量增长下降（尤其是大量 BLOB 读取）
- 数据库迁移成本高

> 💡 **适用场景**：签字记录量较少（日均 < 1000 条），对数据一致性要求极高，且运维团队熟悉数据库管理的场景。

### 4.2 方案二：文件系统存储 / Option 2: File System Storage

**原理**：签名图片保存为文件系统的物理文件，数据库中仅存储文件路径和元数据。

**文件目录结构** 📂：

```
uploads/
└── signatures/
    └── 2026/
        └── 07/
            └── 12/
                ├── sig_1001_001.png    # 签名文件，命名：sig_{documentId}_{sequence}.png
                └── sig_1001_002.png
```

**文件存储 Service** 📁：

```java
package com.example.signature.service;

import org.springframework.beans.factory.annotation.Value;           // 配置值注⼊
import org.springframework.stereotype.Service;                       // Service 注解
import org.springframework.web.multipart.MultipartFile;             // ⽂件上传接⼝

import java.io.IOException;                                         // IO 异常
import java.nio.file.Files;                                         // ⽂件操作
import java.nio.file.Path;                                          // ⽂件路径
import java.nio.file.Paths;                                         // 路径⼯具
import java.time.LocalDate;                                         // ⽇期
import java.time.format.DateTimeFormatter;                          // ⽇期格式化
import java.util.UUID;                                              // 唯⼀ ID

/**
 * 签字文件存储 Service 📂
 *
 * 负责签名图片的本地文件系统存储与读取
 */
@Service
public class SignatureFileStorageService {

    @Value("${signature.storage.path:uploads/signatures}")          // 配置路径，默认 uploads/signatures
    private String storagePath;                                      // 签名文件存储根目录

    /**
     * 存储签字图片文件 💾
     *
     * 数据流动 / Data flow:
     *   byte[] → 按日期分目录 → UUID命名 → 写入文件系统 → 返回存储路径
     *
     * 参数 / Args:
     *   imageBytes: 签名字节数组
     *   documentId: 关联文档 ID
     *
     * 返回 / Returns:
     *   文件的相对存储路径，示例："2026/07/12/sig_1001_abc123.png"
     */
    public String storeSignature(byte[] imageBytes, Long documentId) {
        try {
            // 1. 构造按⽇期分层的目录路径：{storagePath}/2026/07/12/
            String dateDir = LocalDate.now()                         // 获取当前⽇期
                    .format(DateTimeFormatter.ofPattern("yyyy/MM/dd"));  // 格式化为 "2026/07/12"
            Path targetDir = Paths.get(storagePath, dateDir);        // 完整目录路径
            Files.createDirectories(targetDir);                      // 创建目录（含不存在的父目录）

            // 2. 生成唯一文件名：sig_{documentId}_{uuid}.png
            String fileName = String.format("sig_%d_%s.png",         // 文件名格式
                    documentId, UUID.randomUUID().toString().substring(0, 8)); // 取 UUID 前 8 位
            
            // 3. 写入文件
            Path targetPath = targetDir.resolve(fileName);           // 完整文件路径
            Files.write(targetPath, imageBytes);                     // 将字节数组写入文件

            // 4. 返回相对路径（⽤于存⼊数据库）
            return Paths.get(dateDir, fileName).toString()           // 示例："2026/07/12/sig_1001_abc123.png"
                    .replace("\\", "/");                             // 统一使用正斜杠

        } catch (IOException e) {
            throw new RuntimeException("签字文件存储失败", e);
        }
    }

    /**
     * 读取签字图片文件 📖
     *
     * 参数 / Args:
     *   filePath: 文件相对路径，示例："2026/07/12/sig_1001_abc123.png"
     *
     * 返回 / Returns:
     *   文件的字节数组
     */
    public byte[] loadSignature(String filePath) {
        try {
            Path fullPath = Paths.get(storagePath, filePath);        // 构造完整路径
            return Files.readAllBytes(fullPath);                      // 读取所有字节
        } catch (IOException e) {
            throw new RuntimeException("签字文件读取失败", e);
        }
    }
}
```

**对应的 Entity 调整** 🔄：数据库只存路径，不存二进制：

```java
// 签字实体中，signature_data 改为 file_path
@Column(name = "file_path")                           // 签名文件路径
private String filePath;                               // 示例："2026/07/12/sig_1001_abc123.png"
```

**✅ 优点**：
- 数据库轻量，查询速度快
- 文件可直接通过 Web Server 静态文件服务访问，无需应用额外处理
- 备份可分离（数据库 + 文件系统分别策略）
- 文件易于迁移、归档

**❌ 缺点**：
- 数据一致性需应用层保证（文件写成功但 DB 事务回滚？）
- 文件系统管理和备份策略更复杂
- 分布式部署时需共享文件系统（NFS / S3 等）

> 💡 **适用场景**：签字量大（日均万级），对查询性能要求高，有专门的文件备份策略。

### 4.4 Audit Trail：签字合规的核心 / Audit Trail: The Core of Compliance

在合规层面，**仅仅存储签字图片是不够的**。根据 ESIGN Act（美国）和 eIDAS（欧盟）等法规，电子签字必须具备完整的 **Audit Trail**（审计追踪）才具有法律效力。

一个完整的 Audit Trail 需要记录以下信息 📋：

| 字段 | 说明 | 示例 |
|------|------|------|
| **Signer Identity** | 签字人身份标识 | 用户 ID、邮箱 |
| **Timestamp** | 签字时间戳 | 2026-07-12 14:30:00 UTC+8 |
| **IP Address** | 签字时的 IP 地址 | 192.168.1.100 |
| **Device Info** | 设备/浏览器信息 | User-Agent 字符串 |
| **Document Hash** | 签字时文档的 Hash 值（防篡改） | SHA-256: abc123... |
| **Event Log** | 完整操作事件记录 | 打开文档 → 签字 → 提交 |

**Document Hash——防止签字被篡改的关键** 🔐：

```java
import java.security.MessageDigest;                              // 消息摘要
import java.security.NoSuchAlgorithmException;                   // 算法不存在异常

/**
 * 计算文档内容的 SHA-256 Hash 🔐
 *
 * 在用户签字时记录文档的 Hash 值，后续可通过对比 Hash 判断文档是否被篡改
 *
 * 参数 / Args:
 *   documentContent: 文档内容的字节数组
 *
 * 返回 / Returns:
 *   64 字符的十六进制 Hash 字符串
 *
 * 示例 / Example:
 *   computeDocumentHash(documentBytes) → "e3b0c44298fc1c149afbf4c8996fb924..."
 */
public String computeDocumentHash(byte[] documentContent) {
    try {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");  // 获取 SHA-256 算法实例
        byte[] hashBytes = digest.digest(documentContent);              // 计算 Hash
        
        // 将字节数组转换为十六进制字符串
        StringBuilder hexString = new StringBuilder();
        for (byte b : hashBytes) {
            String hex = Integer.toHexString(0xff & b);               // 字节转十六进制
            if (hex.length() == 1) hexString.append('0');             // 补零
            hexString.append(hex);
        }
        return hexString.toString();                                   // 返回 64 字符 Hash
        
    } catch (NoSuchAlgorithmException e) {
        throw new RuntimeException("SHA-256 算法不可用", e);
    }
}
```

### 4.5 方案对比与选型建议 / Comparison & Recommendations

| 维度 | 数据库 BLOB | 文件系统 | 混合存储 (推荐) |
|------|------------|---------|----------------|
| **查询性能** | 中等（BLOB 读写慢） | 快 | 快 |
| **数据一致性** | 强（事务保障） | 弱（应用层保证） | 中等（配合事务消息） |
| **备份复杂度** | 简单（单库备份） | 复杂（两套备份） | 中等 |
| **扩展性** | 差（DB 膨胀） | 好（可加节点） | 最好（支持 S3） |
| **合规支持** | 好 | 需额外设计 | 好（推荐） |
| **运维成本** | 低 | 中 | 中高 |
| **适合场景** | 小规模、一致性优先 | 大规模、性能优先 | 企业级、全都要 |

> 💡 **小恩的推荐** 🎯：
> - **个人项目 / MVP**：用数据库 BLOB 存储，简单省事
> - **中小企业项目**：用文件系统存储，数据库只存引用路径
> - **企业级项目**：用混合存储 + 对象存储（MinIO / AWS S3），同时做好 Audit Trail

```html
            const rect = canvas.getBoundingClientRect();  // Canvas 边界
            return {
```

## 6. 总结 📝 / Summary

本节我们完整讲解了用户签字功能的前后端实现与存储方案，核心要点回顾：🎯

| 层面 | 核心内容 | 关键技术 |
|------|---------|---------|
| 前端 🎨 | Canvas 签名板搭建、Mouse/Touch 事件处理 | `canvas.getContext('2d')`、`toDataURL()`、`toBlob()` |
| 后端 ⚙️ | Spring Boot REST API、Base64 解码、MultipartFile 处理 | `@RestController`、`@RequestBody`、`MultipartFile` |
| 存储 💾 | 数据库 BLOB vs 文件系统 vs 混合方案 | `@Lob`、BYTEA、文件路径引用、对象存储 |
| 合规 🔐 | Audit Trail、Document Hash、签字元数据 | SHA-256、IP/设备记录、时间戳 |

🔴 **关键理解**：

1. **前端核心** 💡：签字功能本质上是**在 Canvas 上捕获用户笔迹并导出为图片**，不涉及复杂的加密或认证逻辑。Touch Events 的 `e.preventDefault()` 和 Canvas 的坐标计算是容易踩坑的地方。
2. **后端处理** ⚡：后端主要负责**接收签字数据 → 校验 → 持久化**，Base64 解码和文件上传是最常见的两种方式。推荐使用 JSON + Base64 方式，无需处理复杂的 multipart 协议。
3. **存储选型** 🎯：**小项目用数据库 BLOB，中大型项目用文件系统 + 数据库引用路径，企业级项目用混合存储 + 对象存储（S3/MinIO）**。
4. **合规不可忽视** 🔐：如果签字具有法律效力，必须记录完整的 Audit Trail（签字人、时间、IP、设备、文档 Hash），确保签名可追溯、防抵赖。
