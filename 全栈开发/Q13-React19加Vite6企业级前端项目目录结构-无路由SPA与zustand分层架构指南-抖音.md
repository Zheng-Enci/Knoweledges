## P01 · 封面

> 卡片职责：抛钩子 + 定锚主题，点破「目录」不是审美问题

- **React 项目目录凭什么按业务域分？**
- 不是审美，是让一次改动只落在一个文件夹里
- **4 条**边界守不住，目录三个月就塌成一坨

## P02 · 可部署与可复用必须分开

> 卡片职责：讲清 apps 与 packages 的分工

- 这两类目录的差别不是体积，是「能不能单独部署」。
- 有入口、有构建配置、能独立跑起来的放 apps，全仓**只允许一个**。
- 只放类型和纯函数的放 packages，它**连 react 都不该 import**。
- 判据很硬：shared 里出现 document 或 window，就是有人把浏览器代码塞进了契约层。
- 这条破了，将来后端想复用同一份类型就复用不了，等于白抽一个包。
- 抽包的成本要用「第二个使用方」来偿付，没有第二个使用方就别抽。
- 类比 🎭：一个是大堂，一个是水电图纸，图纸不该管大堂怎么开门 🏢。

## P03 · 没有路由库，先给导航层找地方

> 卡片职责：说透 App.tsx 塌方的原因

- 页签状态直接堆进 App.tsx，是最省事的开局，也是最贵的技术债。
- 页签每加一个，它就多一段条件渲染、多一个状态变量。
- 三个月后这个文件普遍超过 200 行，改一个页签要读完整份装配逻辑。
- 拆法只有三件：页签注册表、激活态 hook、渲染壳组件，**三个文件各管一件事**。
- 新增页签只改注册表一个文件，App.tsx 永远是同一段装配代码。
- 页签之间若出现共享逻辑，下沉成 hook，别把逻辑塞回注册表。
- 好处不是好看，是「**加页签不用碰装配层**」这个约束被结构固化了 ✅。

## P04 · 页签状态只归应用层

> 卡片职责：给状态归属判据

- 当前在哪一屏是应用级状态，不该进任何一个业务 store。
- 业务 store 的职责是数据，导航属于壳，混在一起谁都不敢重构。
- 读写只走 localStorage **一个键**，全仓只允许一个文件碰这个字符串。
- localStorage 是外部输入：里面可能留着上个版本的旧页签 id。
- 所以读出来**必须做合法性校验**，不合法就落到默认页签 ⚠️。
- 同理要监听 storage 事件，多标签页同时打开时才不会各说各话。
- 还有一个隐藏收益：页签 id 只在一处定义，改名时不会漏改。

## P05 · 四个 store 按写入方切

> 卡片职责：讲 store 切分判据

- 判据只有一句：这份数据的**第一写入方**是谁，它就住进谁的 store。
- token 归认证、会话列表归会话、选中文章归文章、密钥归凭据，四线不交叉。
- 只被一棵组件树用到的状态别进 store，用 useState 就够，否则 store 会变成垃圾场。
- 最容易被忽略的一条：store 里不许放图标组件，持久化序列化时会直接报错。
- 密钥那条是红线：**绝不持久化**，刷新即失，避免被脚本读走 🔐。
- 判断标准回到一句话：谁能写这份数据，谁就该拥有它。

## P06 · 401 处理最容易成环

> 卡片职责：数字 + 因果，讲清注入式依赖

- 请求层直接 import store 取令牌，store 里又调接口发登录请求，就成环。
- 这个环平时看不出来，做代码分割时才炸，报错是「初始化前访问」。
- 报错信息跟业务毫无关系，排查时特别容易走错方向。
- 环一旦形成，构建工具也只能报一个看不懂的错，没人往依赖方向去想。
- 解法是把依赖倒过来：请求层只留「取令牌」和「失权」两个回调。
- 启动时在入口注入一次，请求层从此**零业务依赖**，也不认识任何 store。
- 代价是**多写 3 行**装配代码，换来的是可以放心做分包 ⚖️。

## P07 · loading 用布尔会翻车

> 卡片职责：用并发场景说明计数法

- 两个请求同时在飞，先回来的那个把加载状态置回 false。
- 界面立刻恢复可点，用户再点一次，第三个请求就发出去了。
- 更糟的是按钮 loading 一闪就没，用户以为根本没提交成功。
- 改成**计数**：进入加一，结束减一，**大于零才算加载中** 👍。
- 这样并发语义才正确，跟样式、动画、防抖都没关系。
- 顺手还能拿到「当前几个请求在飞」，做全局进度条也够用。
- 反过来推：一个布尔只有两种状态，可同时飞行的请求却有无数种组合，状态空间根本装不下。

## P08 · 源码直连要三处对齐

> 卡片职责：讲 alias 的收益与代价

- 用 file 依赖加别名直指源码，改类型立刻有提示，不用 build 也不用 link。
- 代价是同一个入口必须在**三处**写一遍：包入口、类型路径、打包器别名。
- 只对齐包入口：编辑器报红，但项目跑得起来。
- 只对齐打包器：能跑，可类型全是 any，等于白写 TypeScript。
- 三处漏一处都不会立刻报错，问题往往在换机器或进 CI 那天才浮出来。
- 这三处本质是同一份事实的三个消费者，谁断链都会让体验降级。
- 还要加一行 React 去重，否则 shared 会拉起第二份 React。
- 那时报的是 **Invalid hook call**，看起来像业务写错，其实是配置 🧩。

## P09 · 主题变量只剩一个落点

> 卡片职责：讲 CSS-first 后的目录影响

- Tailwind 4 把配置从 JS 搬进 CSS，已经没有 tailwind.config.js 可改。
- 主题变量写在入口 CSS 的主题块里，**一个文件**就是全部真相。
- 声明的颜色会自动变成工具类，一份定义同时供变量名和类名使用。
- 所以目录里不该再有 theme.ts，两处定义必然打架，且以谁为准说不清。
- 也不该在组件里**写死十六进制颜色**，那等于在主题系统外开了个后门。
- 一份定义喂给变量和类名两个出口，重复定义就等于养了两套事实。
- 换品牌色那天你会感谢自己：只改一个文件，全站跟着变 🎨。

## P10 · 判断收尾 + 互动钩子

> 卡片职责：给判据式结论 + 唯一一句互动钩子

- 判据：**内部工具型 SPA、页签固定、不需要把当前页分享给同事**，这套够用。
- 要 SEO、要分享深链、要多角色复杂导航，直接上路由库，别用状态硬扛。
- 我按这套骨架搭了 **27 个文件**的演示树，故意埋 6 处违规。
- 校验器一次全报出来，改完变成 28 个文件、0 处违规。
- 约定写进文档没人看，写成一条退出码才叫约束。
- 目录的终点不是漂亮，是**改一处只影响一个文件夹** ✅。
